先建立三个概念

逐个介绍节点之前，先建立三个贯穿全文的概念：模型和服务端如何分工、一轮请求如何流转、什么时候写入数据库。后面的每个节点，都可以用这三点来理解。

1. 模型只负责理解，不会边推理边调用工具 「语义理解」节点只产出一份 JSON，称为 Proposal（模型生成的「理解结果」，表示模型认为用户想表达什么）。模型接口声明了 supports_tools=False（不支持工具调用），所以模型不会自己查数据库，也不会自己修改清单（用户的购物清单，代码中称为 plan）。
模型可以在 Proposal 里提出请求，例如「请帮我查牛奶」或「请帮我加购」。前者写在 lookups（查询请求：请服务端查找商品、菜谱等真实数据）中，后者写在 mutations（变更操作：对购物清单进行增加、修改、删除的请求）中。真正执行这些请求的，是后面的服务端节点。
因此，排查 bug 时先判断：是 Proposal 写错了，还是服务端执行错了？
2. 一轮请求是一条单向流水线 一轮（turn）指用户发出一句话后，系统完成的一次完整处理，对应一次 HTTP 请求。每一轮都从图的「开始」走到「结束」，中间不暂停，也不会回到前面的节点。
用户的下一句话是新的一轮。新一轮会重新读取上一轮写入数据库的内容：清单、待确认问题（pending：需要用户在下一轮补充或确认的信息）和短历史（最近几条对话）。
Prompt（提示词）要求模型始终回答最后一条用户消息，历史消息只作参考。
3. 只有「提交并响应」会写库 前面的节点只做准备工作：理解用户的话、决定路由、准备检索结果、准备清单补丁、组织给用户的回复。
清单、待确认问题和消息记录，都在最后一个节点一次性写入数据库。

这张图在说什么

有了上面三个概念，再来看整张图。Graph 是用 LangGraph 编排的处理流程：图中每个名称是一个节点（node，对应代码中的一个函数），箭头表示执行顺序。

加载上下文 → 语义理解 → 解析校验 → 决定路由
                                      ├─ 只读检索 ─┐
                                      ├─ 清单变更 ─┤
                                      └─ 闲聊/回答/澄清/拒绝 ─┐
                                                             ▼
                                                          生成回答
                                                             ▼
                                                        提交并响应

前四步负责理解和决策。其中只有「语义理解」会调用模型；「决定路由」完全由服务端规则完成。

后四步负责执行、回答和写库。三条分支最后都汇入「生成回答」，但只有「清单变更」这条分支会准备修改清单。

走检索分支时，系统会再调用一次模型。这次调用只能根据已查到的结果组织回复，不能提出新的查询，也不能修改清单。

Proposal 与 Decision

前四步会产生两个核心对象：「语义理解」产出 Proposal，「决定路由」产出 Decision。后续节点主要依据这两个对象工作。简单地说，Proposal 表达「模型认为用户想要什么」，Decision 规定「系统这一轮允许做什么」。

Proposal（模型生成的「理解结果」） 表示模型认为用户这句话想表达什么
  • understanding：用户这句话的意图，以结构化字段表示
  • lookups/queries：查询请求，请服务端去查
  • mutations：对清单加、改、删的提议
  • uncertainties：不确定项，即模型想向用户确认的问题
  • reply：给用户的回复草稿

Proposal 不能决定路由，也不能填写价格、库存、版本号或 task_id

Decision（服务端生成的「执行决定」） 表示这一轮允许系统走哪条流程
  • route：路由，决定当前请求进入哪条处理分支（即图上的分支）
  • mutation_action：「清单变更」节点内部的执行方式
  • write_blocked：是否禁止写清单
  • missing_slots：还缺哪些必要信息（每一项称为一个槽位，即 slot）
  • candidate：候选目标，即还没有正式加入清单、等待确认的目标

Decision 写出后，Graph 只根据 route 选择分支，不再重新解释 Proposal

changes.set 与 style_ref 分别写在哪里

了解 Proposal 的结构后，再看其中最容易写错的地方：字段应该写在哪个位置。最近几次报错，大多是因为模型把字段写到了错误的位置。

字段所属位置表示什么示例场景
changes.set Proposal → understanding 要修改的目标属性：人数、预算、自己做还是买成品、用餐时间、忌口 用户回答「自己做，三个人」
style_ref Proposal → mutations[] 里的一次 add 风格引用：火锅这类场景选哪一种风格（决定配哪一组商品） 用户点「川渝火锅」
pending 里 slot=scenario_style 由服务端提出，写入会话上下文 火锅还没选风格，暂时不能配货（配货：为目标搭配具体商品） 用户说「吃火锅」后，系统追问风格
常见错误 把 style_ref 写进 changes.set：「解析校验」会直接报 MALFORMED_UNDERSTANDING，请求走不到「决定路由」的规则判断。
把风格按钮当成新目标去 add：「清单变更」的授权检查（确认每个改动是否被 Decision 允许）会报 CANDIDATE_GOAL_CONFLICT。
回答火锅风格问题时，Proposal 的正确结构 需要同时包含以下四项：
speech_act=answer_clarification：speech_act（话语类型）表示这句话在做什么，这里是在回答澄清问题。
goal_relation=amend：goal_relation（目标关系）表示这句话和已有目标的关系，这里是修正同一个目标。
focus_ref（目标引用：指向当前正在讨论的对象）指向那份火锅。
mutations: [{ verb:add, candidate_ref:火锅, style_ref:川渝选项 }]：对那份火锅执行 add，并用 style_ref 带上所选风格。

三层失败：先确定问题停在哪一层

上一节的两个常见错误，分别停在「解析校验」和「清单变更」。更一般地说，一轮请求失败时，可能停在下表中的三层之一。排查时先确定停在哪一层，再去对应节点找原因，不要笼统地归结为「模型能力不够」。

失败所在层现象典型错误码 / route清单是否变化
解析校验 提示「没能理解清楚」，或出现 MALFORMED_* 错误 MALFORMED_UNDERSTANDING、MALFORMED_PROPOSAL 没有变化，decide_turn 不会进行路由判断
决定路由 追问澄清问题、拒绝，或只给出只读回答 route=clarify/refuse/chat/answer 没有变化，还没进入清单变更
清单变更 提示「多个目标改动」或「互相矛盾」 CANDIDATE_GOAL_CONFLICT、MIXED_GOAL_CHANGES 没有变化，授权检查拒绝了整批改动

了解整体流程和失败分层后，下面按图的顺序逐个说明八个节点。每个节点都按「作用、输入、输出、规则」四部分说明。节点标题下方的等宽文字是它在代码中的名称；如果带有箭头，箭头后面是该节点调用的主要函数。

节点 1 · 加载上下文

load_context

作用

从数据库读出这一轮需要的全部事实，填入状态（state：本轮请求在各节点之间传递的内存数据），供后面的模型和服务端规则使用。这是每轮请求的第一步，也是唯一负责读库准备的步骤（节点 8 的最终写库不计在内）。

读取的内容不只是聊天记录。模型实际只能看到最近约 6 条对话。完整历史保存在数据库中，但不会全部发给模型。

输入

  • HTTP 请求携带的 session_id
  • 用户本轮说的话（已存入 turn.user_input）
  • 入口页、浏览上下文（view_context）

输出

以下内容写入状态，供后续节点读取。字段名中点号前的部分（如 session、candidate）表示它属于状态中的哪个分区，全部分区和字段见附录。

  • session.turn_mode：本轮所处的任务阶段，分为无任务 / 进行中 / 已完成
  • authoritative（权威事实：从数据库读出、以服务端为准的业务数据）：task_id、plan 版本、state_version、当前目标、requirements（用户明确提出的要求，如人数、预算、忌口）
  • candidate.focus_refs：模型可以直接引用的对象（清单行、待确认目标等）。每个对象用一个 ref（服务端分配的引用编号）表示
  • candidate.goal_candidate（待确认目标）：已经提出、但还没形成清单的目标，例如待确认的火锅
  • candidate.displayed_candidates：上一轮实际展示给用户的候选项
  • 组装给模型的请求（build_request）：当前清单、pending、候选列表（本轮允许模型引用的商品、菜谱等）、协议 schema（Proposal 必须遵守的 JSON 格式）等

规则

  • 不调用模型，不改清单，也不做任何业务决策。
  • 上一轮留下的待确认问题（pending_clarifications）在这里读出。用户本轮的回答会和这些问题一起进入语义理解。
  • 如果上一轮留下了 goal_candidate（例如火锅还没选风格），这里会一并加载。

节点 2 · 语义理解

understand → propose_round

作用

上下文准备好后，本节点调用一次大模型，把返回的原始 JSON 存入 turn.proposal。

模型只负责回答一个问题：「用户这句话在语义上是什么意思？」

模型不负责以下四件事：选择路由、查数据库、写清单、调用工具（supports_tools=False）。

输入

  • 上一节点准备好的上下文（清单、pending、focus_refs、短历史、协议 schema）
  • 最后一条用户消息

输出

原始 Proposal（JSON），常见内容如下：

  • understanding.speech_act：这句话在做什么，如问事实（ask_fact）、要买（request_action）、闲聊（chat）、回答澄清（answer_clarification）、纠正（correct）
  • understanding.goal_relation + new_goal 或 changes：goal_relation 表示这句话和已有目标的关系，常见取值为 new（新建）、append（追加）、switch（替换当前未确认的清单）、amend（修正同一目标）。new_goal 是新目标，changes 是对已有目标的修改。
  • lookups / queries：只是一张请求单，意思是「请服务端去查」，并不是查询结果
  • mutations：加、改、删的提议，还不是执行结果
  • reply：回复草稿。此时它还不能代表「已经加购成功」

写入状态：turn.proposal、turn.model_calls（本轮已调用模型的次数）

规则

  • 理解阶段默认只调用一次模型。检索分支的第二次调用发生在「生成回答」节点，并且只允许写 reply。
  • Proposal 里写了 lookups/queries，不等于已经查到。查询在节点 5 执行。
  • Proposal 里写了 mutations，不等于已经改了清单。修改在节点 6 准备，在节点 8 写入。
  • 口头推荐（例如「您可以试试番茄炒蛋」）如果只出现在 reply 里，不会自动变成待确认目标或清单项。例外是 Proposal 里另外写了 new_goal 或 mutations。
与最近 bug 的关系 用户说「我都可以」，被理解成 ask_fact 加推荐检索。模型在第二次调用中根据检索结果说出了番茄炒蛋。问题出在理解阶段决定查什么，以及回答阶段如何复述；decide_turn 并没有参与选菜。
用户说「可以」，被理解成 add 火锅。问题出在理解阶段：模型没有接上上一句的口头推荐，直接新建了一个目标。

节点 3 · 解析校验

parse_validate → parse_proposal

作用

模型返回 JSON 后，本节点检查它的结构是否符合协议。它相当于协议的守门员：结构不对就记为失败，不修补，也不猜测。

注意：这一步只检查「JSON 是否符合协议」，不判断「模型是否理解了用户」。

输入

turn.proposal（原始 JSON）

输出

  • 成功：写入 turn.parsed_proposal（解析后的结构化对象）和 turn.understanding
  • 失败：写入 turn.halt=failed（halt 是本轮的终止标记）和 turn.error（例如 MALFORMED_UNDERSTANDING）

规则

出现以下任一情况，都会直接判定为失败：

  • 不是 JSON 对象，或包含协议之外的顶层字段
  • 模型写了禁止由它填写的字段：price、stock、task_id、plan_version 等
  • new_goal 与 changes 同时出现
  • changes.set 里出现未知字段，包括 style_ref
  • mutation 或 lookup 的数量超过上限，或 verb（操作类型，如 add / change / remove）不合法
  • Proposal 为空（没有任何内容）
最近实例 用户点了「川渝火锅」，模型却把 style_ref 写进了 changes.set。本节点直接报 MALFORMED_UNDERSTANDING。后续节点不会再处理这份 Proposal，本轮以拒绝结束。

节点 4 · 决定路由

decide_turn → evaluate_gate

作用

Proposal 通过校验后，本节点把已校验的语义和服务端掌握的事实放在一起判断，写出 Decision。这套判断规则也称为门控（gate），对应代码中的 evaluate_gate。

这是整张图中唯一做业务判断的分岔口。之后的分支只看 route，不会回头重新解释 Proposal。

mutation_action（prepare / apply_mutation）只影响「清单变更」节点内部的执行方式，不会在图上多出一条分支。

输入

  • parsed_proposal：speech_act、goal_relation、focus、mutations，以及是否带有 lookups/queries、是否带有 uncertainties
  • 服务端事实（GateFacts）：是否有活跃清单、是否有 goal_candidate、是否有 pending 问题、focus_ref 能否对上、plan 上的分组引用

输出

写入 turn.decision，其中最核心的是 route：

route进入的节点含义
retrieve只读检索用户在问店内事实或要推荐，并且 Proposal 里带了 lookup/query
mutation清单变更允许准备加购、修改或删除（此时还不写库）
chat生成回答闲聊，不写清单
answer生成回答只读回答，没有检索请求
clarify生成回答缺信息或指代不清，需要向用户追问
refuse生成回答请求不受支持，或协议校验失败

规则

下面按判断顺序列出主要规则，用于帮助理解，并非完整的代码逻辑：

  • speech_act=chat 时走 route=chat，一律禁止写清单（即使带了 mutations 也不授权）
  • speech_act=ask_fact 时，有 lookup/query 就走 retrieve，否则走 answer
  • speech_act=unspecified 时走 clarify
  • focus_ref 已填写，但与服务端的对象对不上时，走 clarify
  • goal_relation=new/append/switch 且带有 new_goal 时，先看目标是否 ready（信息已齐全，可以开始准备清单）：ready 就走 mutation + prepare；否则走 clarify，并带上 candidate
  • goal_relation=amend 时，修改当前目标或清单行；如果是在回答 pending 问题，focus 必须对得上
  • 指代清楚的 change / remove，走 mutation + apply_mutation
  • 目标关系不明确，但带有 mutations 或已有清单/候选时，走 clarify（追问「换掉还是加上？」）
关于人数 在当前实现中，目标类型为 meal_plan（用餐方案）且 fulfillment_mode=unspecified（用户没说明自己做还是买成品）时，人数不是阻塞槽（阻塞槽：缺了就不能继续准备的信息）。只要目标里有菜名，就可以进入 mutation/prepare。人数会影响份量，但不妨碍先形成方案。
与最近 bug 的关系 如果「可以」被理解成 request_action（要求执行操作）加 add 火锅，并且 ref 对得上，decide_turn 就会放行 mutation。门控里没有这样一条规则：「上一句只是口头推荐，这一句不算加购授权」。所以问题出在 Proposal，这个节点并没有判错路由。

节点 5 · 只读检索

retrieve

作用

当 route 为 retrieve 时，本节点执行 Proposal 里的 lookups / queries，查询店里的真实候选（商品、菜谱、推荐列表等）。

它不改清单，不写购物车，也不改会话里的 pending。

输入

  • parsed_proposal.lookups / queries
  • 检索预算（每轮 lookup 的数量上限）

输出

写入 turn.read_results：真实的匹配结果列表，包含 ref、名称、match_kind（匹配方式，如精确命中或相似命中）等

之后一定进入「生成回答」，并可能触发第二次模型调用。

规则

  • 检索结果写入状态后有两种用途：供 answer 组织回复文案，或供 mutation 绑定用户点名的那个对象的真实 id。
  • 相似候选（fuzzy：与查询相似、但不是精确命中的匹配结果）可以展示，也可以放进澄清选项。但在用户确认之前，不能直接把它当作用户点名的目标来建清单。
  • 第二次调用模型时 read_only=true（只读模式）：模型只能写 reply，不能再写 lookups 或 mutations。
与最近 bug 的关系 「想吃点甜的」和「我都可以」都走了这条分支。回复里出现番茄炒蛋，是因为检索和回答阶段根据查到的结果组织了回复；decide_turn 并没有把番茄炒蛋选为目标。

节点 6 · 清单变更

mutation

作用

当 route=mutation 时，本节点把「模型提议的改动」转换成「已准备好、但还没写入的清单补丁」。

处理分三步：先授权，检查 Proposal 里的 mutations 是否被 Decision 允许；再编译，把 Decision 转换成对应的具体清单操作；最后准备，由 PlanChangeExecutor（清单变更执行器）生成待写入的变更。

此时还不写库。真正写入发生在节点 8。

输入

  • turn.decision（含 route、mutation_action、candidate）
  • turn.parsed_proposal（重点是 mutations 和 understanding）
  • 必要时读取 turn.read_results，用来绑定用户点名的真实商品或菜谱

输出

结果写入 staged（暂存区：已准备好、但还没写入数据库的结果）：

  • staged.plan_patch / plan_result：准备写入的清单变化
  • staged.pending：本轮新产生的待确认问题
  • staged.context_plan：待写入会话的计划，说明 goal_candidate 和 pending 如何合并
  • 或者 staged.error：授权或配货失败的原因

规则

  • 授权：每个 mutation 都必须被 Decision 允许，而且 ref 必须能对上 focus、candidate 或清单行。
  • 冲突时整批拒绝：一轮里如果有多个互不兼容的目标改动，会报 MIXED_GOAL_CHANGES 或 CANDIDATE_GOAL_CONFLICT。整批都不执行，不会只做一半。
  • 火锅风格：add 火锅场景时，如果缺少 style_ref，配货器会返回 needs_clarification（需要澄清），并生成 slot=scenario_style 的问题和选项。
  • 风格答案：用户点选项后，应该对那份火锅再次 add，并带上 style_ref。不能把风格按钮的 ref 当成新目标去 add。
  • 相似候选还没被用户确认时，发起澄清，询问「你要的是这个吗？」，不直接建清单。
最近实例 用户点「川渝火锅」时，如果模型 add 的是风格按钮自己的 ref，而待确认目标是火锅本身，就会报 CANDIDATE_GOAL_CONFLICT。界面上会显示「多个目标改动 / 互相矛盾」。

节点 7 · 生成回答

answer

作用

三条分支最后都汇入本节点。它负责组织好给用户看的回复，并准备好要一并提交的上下文计划（pending、goal_candidate）。

本节点仍然不写库。

输入

  • route：决定本节点走哪条子路径
  • retrieve 分支：基于 read_results，可能再调用一次模型，得到 answer_reply（检索分支的回复文案）
  • mutation 分支：staged 里已准备好的变更和 pending
  • clarify/refuse/chat/answer 分支：Proposal 中的 reply、uncertainties，以及错误信息

输出

  • staged.message：用户可见的最终回复文案
  • staged.context_plan：待确认问题、待确认目标、展示候选等，交给节点 8 写入
  • staged.kind：本轮结果的类型，取值为 answer / clarify / mutation / refuse

规则

  • 检索分支第二次调用模型时，模型只能根据 query_results（已查到的检索结果）组织回复，不能再提出 lookups 或 mutations。
  • 走 clarify 时，会把模型或门控产生的 pending 问题拼接到回复消息中，包括选项列表。
  • 即使模型的 reply 里声称「已经加购成功」，这段文字在提交前也不会推送给用户。SSE 要等提交（commit）完成后才发送最终文案。
  • mutation 分支不再修改 Decision；要准备什么，mutation 节点已经决定好了。

节点 8 · 提交并响应

respond → commit_graph_turn

作用

这是整轮请求中唯一写库的地方。以下操作都在同一个事务里完成：

  • 校验版本，防止并发请求互相覆盖
  • 写入清单变更（如果有）
  • 写入 pending、goal_candidate、展示候选
  • 写入用户消息和助手消息
  • 写入回执（receipt：本轮最终结果的记录，用于幂等处理和 SSE 最终 payload）

输入

staged 中的全部准备结果，以及本轮的 preconditions（前置条件：session、task 和版本号）

输出

  • message：用户最终看到的回复
  • plan_effect：清单是否变化。keep 表示清单没变，replace 表示清单已更新
  • pending_clarifications：待确认问题，下一轮的 load_context 会重新读取
  • action_results：本轮执行结果的记录，例如只读完成、澄清、拒绝、提交等

规则

  • 校验失败时，业务改动和成功回执都不会提交，只提交一条「拒绝」回执。
  • 澄清也是一次正常的提交：pending 会保存到数据库。用户的下一句话会开始新的一轮，并从这里保存的内容接着读取。
  • 在界面上点右上角的「+」，前端会清掉 session_id 并新建 session。旧会话仍保存在数据库里，只是当前页面不再连接它。

例题 · 沿流程图排查最近的会话

看完八个节点后，用一个真实会话练习如何沿流程图定位问题。会话 sess-cbf915f0c2aa 中连续出现了几个问题，按节点拆开如下：

用户输入经过的节点问题所在及原因
想吃点甜的 1→2→3→4(retrieve)→5→7→8 只读检索加回答，plan_effect=keep。这一轮没有问题，只是口头建议了食材。
我都可以 同上 仍然是 ask_fact，走检索，再由第二次模型调用生成回复。回复里出现番茄炒蛋，是回答阶段按检索结果复述的结果，番茄炒蛋并没有成为清单目标。问题出在理解阶段和提示词锚定，与 decide_turn 无关。
可以 1→2→3→4(mutation)→6→7→8 Proposal 写成了 add 火锅，decide_turn 放行。由于缺少风格，生成了 pending scenario_style。问题出在节点 2：模型没有接上上一句对番茄炒蛋的口头推荐，直接新建了火锅目标。
川渝火锅 停在节点 3 或节点 6 如果写成 changes.set.style_ref，会在节点 3 解析失败。
如果 add 了风格按钮，会在节点 6 报 CANDIDATE_GOAL_CONFLICT。
如果「可以」按设计工作，流程应该是怎样的？ 上一句助手口头推荐了番茄炒蛋，用户表示同意。此时：
节点 2 应产出 request_action + new_goal/meal_plan/番茄炒蛋 + lookup，或者产出一个明确指向检索到的菜的 add；
节点 4 给出 mutation；
节点 6 绑定真实 id，并准备清单。
在没有清单、也没有待确认目标时，不应该突然 add 火锅。

沿流程图排查 bug 的步骤

最后，把全文内容整理成一份排查顺序。拿到一轮异常请求的 trace 或界面表现时，按下面的顺序逐项确认：

  1. 清单变了吗？ 看 plan_effect 是 keep 还是 replace。
  2. 停在哪一层？
    • 报 MALFORMED_*：看节点 3，检查 Proposal 的 JSON 结构（尤其是 changes.set 里有没有非法字段）
    • route=clarify/refuse/chat/answer，且没有 mutation：看节点 4，检查 speech_act、focus 和 goal_relation
    • 出现 mutation_refused（变更被拒绝的执行记录）或「互相矛盾」一类的文案：看节点 6，检查 mutations 是否和 candidate 对得上
  3. 模型调用了几次？ model_calls=1 通常表示只做了理解；等于 2 说明走了检索分支，回答阶段又调用了一次。
  4. pending 里有什么？ 有 scenario_style，说明火锅缺风格；有 mixed_goal_changes，说明上一轮的变更授权发生了冲突。
  5. 口头推荐算不算目标？ 如果推荐只出现在 reply 里，没有对应的 goal_candidate 或 mutations，用户下一句说「可以」时，不会自动关联到那道菜。这是当前的产品行为，也是最近 bug 的根源之一。

附录 · state 里有哪些变量

前面各节经常出现 turn.proposal、staged.message 这样的字段，它们都存放在 state 中。state 是本轮请求在各节点之间传递的内存数据，定义在 backend/app/agent/graph/state.py。本节列出其中的全部变量及其含义，供排查时查阅。

每个 HTTP 请求都会新建一份 state。新建时只填入会话和本轮的 ID，以及用户这句话，其余内容由「加载上下文」从数据库读出。请求结束后，state 随即丢弃，不会保存。多轮对话之所以能接上，靠的是「提交并响应」写入数据库的业务数据，下一轮再由「加载上下文」读回。

state 分成六个分区，每个分区只由固定的节点写入。把鼠标移到下表的某一行上，右侧流程图会高亮写入该分区的节点。

分区保存什么写入它的节点
session 这次请求的身份信息，以及本轮所处的任务阶段 新建 state 时填入各项 ID；加载上下文补上 turn_mode
authoritative 从数据库读出、以服务端为准的业务事实 加载上下文
candidate 模型可以引用的对象、正在讨论的目标，以及上一轮展示过的候选 加载上下文
turn 本轮的推理过程：用户输入、Proposal、Decision、检索结果和终止标记 语义理解、解析校验、决定路由、只读检索；清单变更也会写入它自己查到的检索结果
staged 已准备好、但还没写入数据库的结果 清单变更、生成回答
result 提交事务的结果 提交并响应

还有一些数据不放在 state 里，而是挂在 runtime（TurnRuntime：本轮的运行环境，持有数据库会话、模型接口等）上，例如候选集合、发给模型的上下文快照，以及返回给前端的完整响应。在 state 里找不到这些内容时，可以去 runtime 上找。

session：请求身份

字段含义
session_id会话 ID，由 HTTP 请求带来
owner_id会话所属的用户。加载上下文用它校验会话归属，不匹配时报 SESSION_FORBIDDEN
turn_id本轮的 ID，格式为 turn-{request_id}。request_id 是这次请求的编号：同一个 request_id 重复提交时，已完成的请求会直接返回原来的回执，不会重新执行
turn_mode本轮所处的任务阶段：taskless（无任务）、active（进行中）、completed（任务已完成、已取消或已被替换）。由加载上下文根据数据库里的任务状态得出

authoritative：数据库里的业务事实

字段含义
task_id会话当前的任务 ID；没有任务时为空
plan_id、plan_version当前清单的 ID 和版本号，取自任务中保存的清单
state_version任务状态的版本号。清单每次写入都会更新它，节点 8 用它防止并发请求互相覆盖
session_version会话的版本号，同样用于防止并发覆盖
pending会话中仍在等待用户回答的问题
target_kind、target_id、target_name会话当前围绕的真实目标（例如某道菜或某个商品）的类型、ID 和名称。用户说「补人数」这类追问时，可以直接对应到这个对象，不必重新查找
requirements用户明确提出的要求，例如人数、预算、忌口

candidate：可引用的对象和待确认目标

字段含义
focus_refs模型可以直接引用的对象，例如清单行、待确认目标。每一项都带有服务端给定的类型
goal_candidate待确认目标：已经提出、但还没形成清单的目标。它绑定了当时的任务和清单版本，版本变化后就会失效，不能再用来补充信息或建清单
displayed_candidates上一轮实际展示给用户的候选，从会话上下文中恢复

turn：本轮的推理过程

字段含义
user_input用户本轮说的话
proposal模型返回的原始 JSON，尚未校验
parsed_proposal通过解析校验的 Proposal 对象。后续节点都从这里读取 Proposal，但只有决定路由会据此选择分支
understandingProposal 中 understanding 部分的 JSON 形式
decisionDecision 的内容，主要包括 route、mutation_action、write_blocked、missing_slots、candidate，以及内部诊断码 reason_code。解析失败时，这里是 route=refuse，reason_code 就是对应的错误码
read_results检索结果列表，由只读检索或清单变更节点写入
model_calls已调用模型的次数，语义理解之后为 1。检索分支的第二次调用发生在生成回答节点内部，不会回写这个值。要确认是否有第二次调用，请看 trace 中的 model_call 事件（call_number 为 2）；「排查步骤」第 3 条说的调用次数，指的也是 trace 中记录的次数
answer_reply检索分支第二次调用得到的回复。它只在生成回答节点内部使用，最终组织进 staged.message，不会写回 state
halt提前终止的标记：stopped（用户停止）、timed_out（超时）、failed（模型调用失败、Proposal 校验失败等）。正常情况下为空
error提前终止时的错误信息，包括 code、message、retryable；理解类失败还会带上 understanding 标记

staged：准备好、但还没写库的结果

字段含义
kind本轮结果的类型：mutation（准备改清单）、clarify（追问）、answer（回答）、refuse（拒绝）
message给用户的回复文案，由生成回答节点组织。节点 8 写入清单改动后，可能会在后面附上清单摘要
pending本轮新产生的待确认问题
context_plan要写入会话上下文的计划，说明待确认问题、展示过的候选、待确认目标分别如何更新
preconditions本轮开始时记录的 session_id、task_id、state_version 和 session_version。节点 8 在事务中把数据库里的最新值和它比对，不一致就报 STALE_STATE，本轮改动不写入
error准备阶段的失败原因。授权冲突时带 conflict 标记，理解类失败时带 understanding 标记
mutations通过授权的 mutation 列表，包括服务端编译补出的操作
batch准备好的全部变更步骤，节点 8 按顺序逐步执行

下面这些字段记录第一步变更的明细，内容和 batch 的第一项相同：

字段含义
verb这一步的操作：add、change 或 remove。修改人数也按 add 处理
target_kind、target_idadd 时要加入的真实目标的类型和 ID
operationadd 与现有清单的关系：replace（整份替换）、append（追加一组）、resize（按新人数调整已有的一组）
switching是否换掉当前清单。为 true 时，节点 8 会新开一个任务
plan_resultadd 时准备好的配货结果，节点 8 用它合并进清单
argsadd 时交给配货服务的内部参数，例如目标、人数、预算、忌口
plan_patchchange 或 remove 时准备好的完整新清单，节点 8 直接用它替换旧清单
group_id这一步涉及的清单分组
sku_id、quantity修改件数时的商品 SKU 和目标件数

result：提交结果

字段含义
plan_effect清单是否变化：keep（没变）或 replace（已更新）
committed本轮是否真的保存了清单改动
receipt本轮回执的标识：request_id、assistant_message_id、message_sequence、task_id、status
action_results分区里定义了这个字段，但提交并响应节点不会回写它，所以它在 state 中一直是空列表。本轮的执行记录要看返回给前端的响应中的 action_results
response在 state 中始终为空，完整的响应体保存在 runtime 上
排查时先看这几个字段 本轮有没有提前结束：看 turn.halt 和 turn.error。生成回答节点内部的失败只会体现在 staged.error 里。
走了哪条分支、为什么：看 turn.decision 里的 route 和 reason_code。
准备出了什么结果：看 staged.kind 和 staged.error。
准备好了却没写入：常见原因是节点 8 发现数据库里的版本和 staged.preconditions 不一致（STALE_STATE）。
清单最后有没有变：看 result.plan_effect 和 result.committed。
