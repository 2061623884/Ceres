# Ceres v1 实现规划

日期：2026-10-04。用户已整体确认，执行入口见 [Ceres v1 TASK](../../tasks/ceres-v1.md)。当前阶段和业务规则以 [PROJECT](../../PROJECT.md) 为准；本文件只记录交付取舍、依赖顺序和验收安排，执行状态与证据由 TASK 维护。

## 已确认的发布定义

- Ceres v1 是限定导购演示版：模拟供给下的单菜采购及基础零食、饮品选购，止于明确确认加购。沿用 PROJECT 九类流程，不以完整品类筛选、多 SKU 比较、人数、长期记忆或 Mercury 售后作为前提。
- 本机可复现交付：源码、模拟数据、索引、模型与 Prompt 的版本明确，按说明可重新启动和复演，不依赖只有当前运行工作树才存在的代码或未记录的数据。
- 正式固定用例每轮模型最终回复不超过 15 秒，从客户端提交到收到最终回复计时。显示处理中不代替最终回复；错误、超时和人工重发不算该轮通过。每个固定用例在相同冻结版本下独立重复 2 次，保留全部失败；不据此声称长期可靠性或 P95。
- 供给不足先预览并保留旧清单；用户明确选择只购买可售部分后才形成部分采购清单，说明仍缺必需食材，再经单独明确确认后加购。预算与当前会话明确的食材排除仍生效。术语见 [GLOSSARY](../../GLOSSARY.md)。
- 以仓库内现有 64 商品 fixture 为基础；果汁正向采购仍必验，允许只补齐该案例所需的最少商品及已核资料。最终数量在核对后记录，不提前宣称一定是 65 件。此前完整 321 商品／257 来源商品冻结方案已被本次决定替代；原开发库保留，v1 不依赖它重建，不以新增 SKU 数量当成功指标。
- 向量语义检索是 v1 必交付项，使用项目现有 embedding／索引／hybrid 检索链路；0 向量、词法降级或仅设置 `hybrid` 不算交付。明确条件和可售性仍由既有业务校验保证，向量相似度不能取代它们。

## 规划时核查

以下保留规划阶段的核查依据；实施后的固定输入与结果以各 TASK 为准。01 的供给已确定为 65 商品，见 [供给资料](../../work/ceres-v1/01-fixture-baseline/SUPPLY.md)。

- 清单改选已接通现有 plan-revisions；默认必需项勾选、pantry 未选，服务端选择／版本与页面金额、确认和购物车新增在限定案例中一致。最终页面两次使用受控模型 provider，真实业务 API，不能称为真实模型稳定性证明。
- 单菜实际模型 API 固定用例两次通过，但页面第二轮 ACK 超时，任务仍待验收。零食两次成功供给回放也不等于饮品、主推理由或所有 SKU 已通过。
- 既有代理路径问题有针对性的修复证据，后续仍记录约 45 秒模型超时，其具体服务或网络原因未知。不能直接归因为语义理解失败，也不能只降低超时配置就宣布解决。
- 当前有效语义实现有未提交代码，检索索引有 0 向量及 `VECTOR_INDEX_MISSING`，部分运行库饮品候选的中文名／品类需要核对。HEAD、fixture、当前运行库和旧评测窗口不能混称同一已验收版本。
- 供给不足的当前实现与 PROJECT 预览规则存在差异；换菜、撤回、约束、追加和关系澄清需核对当前最终版本，历史全量语义 A/B 保持停止。
- 当前开发 runtime 为 64 个 demo 商品及 257 个来源商品、321 Offer、111 购买模板、2 条商品审核、1 门店和 1 配送报价；根 fixture 为 64 商品、55 条显式 Offer、105 道菜谱。既有 seed 会为其余 9 件 approved 商品按固定价格规则生成模拟 Offer；未补果汁前，fixture 空库应有 64 商品／64 Offer、105 菜谱和 6 个普通购买模板，检索投影应有 169 文档。这些是现有代码推导的重建预期，本轮没有实际重建；补充果汁后按最终输入记录数量，不能照搬 169。
- 应用启动只初始化 schema，不自动 seed；现有 `scripts/seed_runtime.py` 会先导入 `SOURCE_DATABASE_PATH` 再写 fixture。本机来源库存在，直接重跑会混入 257 来源商品；脚本是 upsert，不能在当前 321 库上重跑后宣称已缩减。v1 需要显式排除来源导入，在独立空库重建。现有 DB／source／索引配置可以继续使用，无需新增业务状态。
- 本轮只读 Settings 已有 `Qwen/Qwen3-Embedding-0.6B`、1024 维、SiliconFlow endpoint 和 embedding 凭据（不写密钥）；无需再索取已有配置。当前索引为 321 SKU／426 文档／0 向量，实际构建、查询及耗时尚未验收。远端模型实际权重 revision 未获独立证明，不将模型名或本地构建标签冒充远端权重版本。
- 既有 [RAG 交付入口](../rag/README.md) 记载只读接线和词法链路已有，真实向量质量尚未验收。旧评测入口要求 dev／holdout 最少标注数量，而其引用的 `verification/rag/annotation-set.json` 当前不存在。不得修改 lint 门槛制造旧评测通过；v1 用明确的业务查询和向量分支证据做限定验收，不冒称旧正式通用 RAG 质量评测已通过。

证据入口：[采购与单菜 TASK](../../tasks/purchase-selection-and-single-dish.md)、[零食 TASK](../../tasks/snack-selection.md)、[旧语义 TASK](../../tasks/semantic-contract.md)、[此前超时诊断](../../work/model-timeout-case/IMPLEMENTATION.md)。本轮只读核查，没有新增模型采样或运行验收。

主依赖顺序是 **01 → 02 → 03 → 04 → 05 → 06**。旧超时日志的只读归因可与 01／02 并行；正式延迟验收必须包含真实 query embedding，广泛实际模型端到端验收等响应问题收口后再进行。04 内部保留“先采购改选、后单菜”的顺序。现有架构、匿名身份、会话状态和清单接口继续使用，不新建记忆或重复状态；不默认增加 ACK 字符串路由、重试、兜底或异常捕获来掩盖模型问题。

本地 [v1 总任务](../../tasks/ceres-v1.md) 已链接六项依赖编号 TASK。同一主会话协调共享 fixture／索引／语义代码的修改；旧 TASK 只作为适用证据引用，不复制或覆盖其状态。数据及 seed 入口归 01，检索归 02，超时归 03，供给预览及清单一致性归 04，商品推荐归 05，统一发布证据归 06。

向量构建复用现有 `scripts/build_retrieval_index.py` 并显式提供冻结候选库；通过现有 `--env-file` 入口读取配置，避免离线 CLI 的进程环境与应用 Settings 使用不同 embedding 契约。query／document 指令、模型标识、维度和 revision 字符串按实际配置记录；空 revision 合法但不能证明远端权重固定。语义表达检查包括低词面重叠的正向查询及相邻分类／明确条件的负向查询，保留向量召回、融合与过滤记录，不要求每个精确点名都由向量胜过既有精确匹配。后续商品资料变化必须重建受影响向量和最终索引，再冻结验收版本。

01／02 还须确认已核实的果汁与甜味依据实际进入商品检索投影。当前 `project_sku_row` 使用名称、品牌、`usage_tags` 及已声明／已核映射食材，不读取通用 description；优先复用现有会被投影的字段，只写有来源的资料，不仅保存在未索引的说明中。若核对后仍无可信甜味正向候选，如实记录具体供给缺口并提出最少补齐方案，不能用推荐文案替代商品事实。

## 九类验收的具体覆盖

九类不等于九条输入；一类包含不同业务出口时分别固定子用例，每个子用例各独立重复两次。以下是输入及状态的候选，最终商品／菜品范围待供给核对后冻结；期望行为沿用已确认 PROJECT 规则，不事后挑成功样本。

| 类别 | 至少覆盖的具体路径 | 当前差距 |
| --- | --- | --- |
| 1 点名菜品 | 点名一道可售菜 → 商品包装／数量／价格一致 → 明确确认。 | 完整真实模型页面两次证据不足。 |
| 2 模糊推荐 | 无名自己做一道菜；必要澄清可完成或跳过；明确预算和“不吃鸡蛋”能影响推荐。主推一道且理由有依据。 | 有限 API 已通过；同版真实页面无异常和 15 秒门槛未通过。 |
| 3 换或撤回 | 未确认单菜“换一个”得到不同、符合已生效条件的目标；另例撤回不加购。 | 有实现和受控测试，v1 固定真实页面待验收。 |
| 4 追加与关系 | 明确追加第二道菜；在菜品清单追加商品；新目标关系不明时先澄清。旧分组保留，同 SKU 按现有分组购买数量贡献汇总。 | 当前最终版本真实证据不足，不扩展菜间推荐、食材优化或多组原子局部替换。 |
| 5 改选与确认 | required／pantry 默认选择；勾选油、取消番茄；金额／版本／刷新恢复／确认数量／购物车新增一致。已有空选择恢复保持相关回归。 | 受控页面已有限验证，正式同版端到端保留此回归。 |
| 6 供给不足 | 必需食材缺项：预览不建清单；用户选择可售部分才建部分清单；另行确认。覆盖没有旧清单和有旧清单时的保留。 | 现有直接 partial 建单／确认期待与新规则冲突，确需修改及相应测试。 |
| 7 具名商品 | 点名零食及具名饮品，明确规格／销售包装和购买件数，不将首候选随意绑定成用户要求的商品。 | 通用代码存在，当前演示供给上的正式两次待验收。 |
| 8 品类／偏好 | 零食品类、果汁品类、“甜的”有明确描述依据的正向选购；资料不足时必要澄清及正确退出。各路径单独验证。 | 已验零食是展示两候选供选择；v1 所需单款主推及理由、饮品和偏好仍有缺口。 |
| 9 无匹配 | 冰淇淋等冻结供给外请求；覆盖已有待确认清单和已有购物车时保持原内容。不推荐其他品类。 | 有限定受控和 API 证据，正式真实页面两次仍待验收。 |

所有正式路径核对整份采购清单的已选金额及明确的食材排除条件；pantry 勾选后计入预算，未勾选不代表用户家中已有。选定、生成清单、预算协商与确认加购沿用 GLOSSARY 的不同定义；不得把普通“好的”当加购授权。已加购内容不因新目标、无匹配或预览被静默改变。

## 验证与文档安排

- 只运行各阶段必要的相关测试；行为修复先使用现有公共 API 和受控 provider 锁定预期，再验证实际模型与页面，不将这些证据混为一类。
