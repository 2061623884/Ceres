# Ceres1 V4 非人工评测规格

日期：2026-10-07。由 `/to-spec` 综合本会话已确认的六项决定和候选源码事实形成；执行状态与证据入口只在 [TASK](../../tasks/ceres-v4-evaluation.md) 维护。

## Problem Statement

Ceres1 V4 已开发完成，但开发交付、旧版本测试和已经使用的留出样本不能证明最终候选通过验收。用户需要可复跑的非人工评测，核对实际业务结果、授权和约束，保留失败与证据，并按严格门槛给出结论。

## Solution

对 Ceres1 V4 形成可复跑、能核对业务结果的自动评测和验收记录。参考 ChatGPT 会话“设计评测集”（6ac5e2ae-3570-83ee-b169-53e5d4b943c9）的任务级方法，重新依据 Ceres1 的源码、接口与数据设计，不复制 Ceres2 的实现事实或实测结论。

用户已确认：

- 覆盖现有零食/饮品选购、采购修改与明确确认、政策与角色切换、售后后继续采购、专题商品；现有记忆能力另列组件评测。
- 业务终态、金额、数量、约束和授权由代码判定。模型裁判仅输出语义诊断与证据，未人工校准前不进入硬性验收门槛；人工评测不在本次执行范围。
- 发现产品缺陷后保留失败、最小复现和修复任务入口，继续独立场景；本轮不修改产品行为。评测器自身错误须修复并保留原始无效执行。
- 首版 60 个场景：40 个开发/回归、20 个新验收；20 个核心场景各独立执行 3 次，其他 40 个各一次，共 100 次任务执行。先验证 20 个代表场景的评分规则，再开展完整执行。
- 固定必验场景与硬约束全部通过、关键违规为零、每轮最终回复不超过 15 秒；功能和性能分别报告，任一不满足都不宣称自动验收整体通过。

用户已确认最终产品候选为 `work/.ceres-next-08` 的 `ac895fd620af617fa31f4e0006841a4d6a89cd53`。root/main `ee7ce10`、integration `17d77b8` 不混用。08 包含晚于交接文档的预算继承修复，不能沿用旧文档的“源码未修”作为当前事实；候选冻结仍不等于已验收。

## User Stories

1. 作为验收负责人，我希望锁定指定 V4 候选，以免混合不同工作区或版本的结果。
2. 作为维护者，我希望冻结源码、未提交输入、数据、索引、实际模型和 Prompt，以便解释和复跑结论。
3. 作为执行者，我希望每次任务有独立进程、数据库、owner 和会话，以免前一条失败污染后一条。
4. 作为导购用户，我希望零食和饮品通过分类、筛选和澄清形成合格选择。
5. 作为导购用户，我希望数量、预算与商品替换正确应用，并保持当前任务与独立任务的约束边界。
6. 作为导购用户，我希望只有明确确认才写入购物车，重复提交不会重复加购。
7. 作为咨询用户，我希望比较和政策问题有实际商品或模拟政策依据，咨询不会提交申请。
8. 作为聊天用户，我希望角色切换由我的选择决定，拒绝切换不会变更角色或执行另一角色业务。
9. 作为售后用户，我希望系统只处理我的指定订单，资格、申请数量和回执与实际记录一致。
10. 作为售后用户，我希望售后成功、失败或拒绝后仍能选择继续采购，已完成申请不会重放。
11. 作为专题用户，我希望从真实专题入口和气泡完成选购，买到正确的成品商品。
12. 作为记忆功能使用者，我希望显式保存、更新、删除和跨会话读取正确，其他 owner 无法读取我的内容。
13. 作为记忆功能使用者，我希望当前要求优先，临时预算不会误存，自动提取和 Dream 不破坏显式内容。
14. 作为验收负责人，我希望正常完成与合规拒绝分别计数，准备失败、脚本失败和未执行留在分母内。
15. 作为验收负责人，我希望看到核心场景三次均达标数、逐轮时间、P50/P95，以及未采集的时间缺口。
16. 作为维护者，我希望模型裁判意见和证据独立可读，不能以未校准裁判替代业务事实。
17. 作为执行者，我希望主模型、Kev、售后和后台记忆调用与 usage 分项记录，缺失信息保持未知。
18. 作为产品负责人，我希望失败有最小轨迹、复跑入口和修复任务，保留失败版本而不在评测途中修产品。
19. 作为审阅者，我希望区分离线检查、真实模型/API、自动浏览器和未执行的人工评测。

## Implementation Decisions

一条评测样本对应一次用户目标，包含初始业务条件、用户输入及有界后续操作、成功条件、硬约束、禁止行为、依据和允许变化；不要求唯一措辞或唯一合格 SKU。政策咨询、商品比较、确认加购和售后申请按各自目标判断，不能一律要求产生订单。

开发/回归与新验收按场景族分组，等价改写不跨集合。旧公开场景可作为回归；已经执行或用于修复的旧留出不重新命名为未见。新验收集在正式运行前冻结，记录其来源、摘要和首次执行版本；独立于当前源码修改不等于经过严格盲测或可据此宣称统计泛化。

每次执行使用独立 owner/session 和可重建的初始业务状态，隔离数据库、索引和记忆状态。一个场景失败不得使其他场景或售后覆盖一并消失。场景前提无法建立时，记录准备失败和未执行步骤，不冒称业务判断失败或成功。

关键违规包括未授权业务写入、错误 owner/订单操作、未选择的服务切换、重复执行已完成步骤，以及可查证的虚假商品/政策/业务状态。业务层拦截错误动作与实际错误写入分别计数。无法由代码判定的自由文本事实保留模型诊断与未知，不能将诊断未报错当成事实错误为零的证明。

正确拒绝或澄清可以是预标注的达标终态，但应单列，并另报正常可完成任务结果。脚本确认、点击与模拟结算只验证系统处理能力，不作为真人转化、采纳或真实履约的证据。

默认执行在首批 20 次后结束；主会话核对评分有效性后，继续同一冻结批次剩余 80 次。继续前核对产品、评分器、样本、种子、索引和实际供应商配置；不混用不同条件。初始订单可由现有模拟购物车/结算准备，送达时间和组件记忆前提可在隔离库准备，必须标为准备动作，不计作智能体成功。

## Testing Decisions

主要测试接缝是现有公共 HTTP/API/SSE，范围和候选已由用户确认；专题与气泡采用真实浏览器。Dream 无公共触发 API，因此只通过现有服务入口作组件验证，不将内部触发写成用户旅程。不新增产品测试专用接口或 schema。

评分器测试针对外部可观察行为：缺失金额/预算不能以零通过，错误价格即使内部算式一致也失败，拒绝切换仍变更角色必须计关键违规，准备失败不得从分母消失。先离线检查评分器，再核对 20 个代表场景实际结构与判分；若脚本错误，保留原记录并修复后重新冻结；产品失败不改标准或救场。

确认场景检查实际商品、数量、Offer 价格及购物车总额；单菜检查必需食材与默认选择，不以购物车非空作为充分条件。政策检查本轮读取依据；售后检查指定订单、申请记录与重复执行。记忆检查 owner 隔离、显式内容与当前条件优先，后台事件和调用单列。

复用当前聊天/API/SSE、清单确认、购物车、模拟订单、售后和记忆公共接口，以及现有多轮 runner 的操作与取证能力。补充必要的机器判分、独立重复执行和汇总，不引入测试专用产品 API 或通用评测平台。气泡和专题入口使用自动浏览器验证，并与 API 结果分开记录。

受控测试、真实 Kev、真实角色主模型、自动浏览器与模型裁判分别报告。记录实际加载的源码及 dirty 输入、fixture、索引模式/摘要、模型配置、Prompt/裁判规则与样本摘要；Git HEAD 不能单独代表带未提交变动的执行版本。

既有 hybrid/embedding HTTP 402 记录是历史运行阻塞。保留此前“不重试、其余验证使用 lexical”的决定；最终候选若仍采用 lexical，报告必须明确限定检索条件，不宣称 hybrid 通过。

每轮保留输入、SSE/可见结果、相关工具结果、前后业务状态、检查证据与实际时间。首个有用结果和最终完成时间分别统计；没有采集到的时间、usage 或价格保留未知，不将动画、占位话术或缺失值当作有用结果或零成本。

主模型、Kev、Mercury 与后台记忆/Dream 的调用和 usage 分项汇总，背景调用另列。无可靠定价或 usage 覆盖不完整时，金额成本保持未知，并记录覆盖率。

## Further Notes

交付版本化样本、可复跑命令、逐场景原始轨迹与代码检查、模型语义诊断、JSON/Markdown 汇总以及失败最小复现入口。原始记录放在 `work/ceres-v4-evaluation/`，样本放在 `evals/v4/`。

汇总须同时记录计划场景数、计划执行数、实际尝试/完成/达标/失败/准备失败/未执行数，公开分母及分组；未执行或准备失败不得因从成功率分母剔除而满足整体验收。重复结果同时报告逐次成功率与 20 个核心场景三次均成功的比例。

硬约束、关键违规、正常完成与合规拒绝、路由/政策/记忆组件结果、逐轮时延及 P50/P95、模型调用与 usage 覆盖分别报告，不合成无解释的总分。最终结论只适用于冻结版本、数据和运行条件；人工表达、真人行为和用户本人确认继续保持未验证。

## Out of Scope

不扩展商品库或产品功能，不修改历史 V1/V2/V3 验收状态，不恢复历史全量 A/B 或模型选型，不运行人工评测，不宣称真人购买意愿、真实交易或履约，不推送、不部署。
