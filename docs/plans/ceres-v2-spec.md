# Ceres V2 实施规格

产品来源：[PROJECT-next](../../PROJECT-next.md)，读取日期 2026-10-05。用户已明确在现有 Ceres 开发 V2。规格与票据由主 Agent 依授权发布，继承输入及 Git HEAD 见 work/ceres-v2/00-baseline/baseline.json。

## Problem Statement

已有限定导购能准备单菜和基础商品清单并明确确认加购，已有真实向量与固定输入重建证据；整体 V1 正式页面验收仍有失败和缺失。V2 要解决人数和明确多菜的用量核算、可乐 SKU 决策、跨会话重复沟通与复购，以及模拟订单无法被同一用户的墨墨查询的问题。不得通过叙事将旧缺口改写为已验收。

## Solution

沿用现有 FastAPI、LangGraph 请求级流程、匿名 owner、会话/任务 State、采购清单修订和统一确认接口。新增业务进入现有事实与执行边界，不建立第二份采购状态或模型授权。

分别交付九张完整业务切片票据。每票经过公共行为 TDD、最小代码、相关回归、本地提交、Standards/Spec 双轴审查。产品总验收包含代表性演示和用户本人操作，技术通过与人工待验收分别记录。

## User Stories

1. 用户指定番茄炒蛋 4 人份时，看到番茄需 600g、买两包 500g，鸡蛋需 6 枚、买一包 6 枚；剩余与需求区分，默认选择规则沿用。
2. 用户修改人数时，需求、包装数量、金额、版本和最终购物车一起更新，确认前不加购。
3. 用户明确追加第二道菜时，已有分组保留，共用兼容食材先合计需求再算整包数量，每道菜用量来源仍能查看。
4. 用户手动选择采购部分或指定商品件数时，自己的选择仍保留，直接商品件数不被菜谱用量合并吞掉。
5. 用户移除某道菜或改变人数时，共用食材重新核算，已购数量及明确预算不被静默放宽。
6. 某销售规格缺货时，得到仍满足同食材、数量、预算与排除条件的其他规格/多包装方案并看到规格差异。
7. 整种必需食材无供给或不足时，看到缺项及受影响菜品，旧清单/购物车保留；明确选择可售部分后建部分清单，仍需单独确认。
8. 用户在可可聊天中比较可乐时，看到最多五个有核查依据的候选和整包价格、每件容量、包装内件数、总容量与每升价格。
9. 用户按品牌、容量、罐/瓶、单件/多件和模拟价格调整条件时，候选随有效条件更新；无匹配如实说明，不改为其他品类。
10. 用户从浏览入口询问可乐时，已有入口上下文用于理解，候选有真实 SKU 引用；自然语言和气泡选定后进入现有清单与确认流程。
11. 用户说“记住以后先列差异”或“长期不要鸡蛋”时，偏好/纠正按明确来源持久保存，新会话按需读取，当前明确需求优先。
12. 用户询问、纠正或删除记忆时，收到真实保存内容或变更结果；删除记忆不删订单、清单或消息。
13. 用户正常交流结束后，后台提取稳定信息；不把临时预算或人数自动写为长期偏好，不主动展示自动提取或整理过程。
14. Dream 去重和清理过时自动记忆时，不丢失有效显式保存内容，不以推测覆盖用户明示偏好。
15. 用户参考上次方案采购时，系统查询有结构化来源的历史参考，生成新的本次清单，重查库存价格、应用本次人数预算/排除并重新确认。
16. 用户在购物车独立模拟结算时，生成自己的持久订单，购买时商品、数量和单价快照固定，结算和清空购物车结果一致。
17. 用户进入墨墨、打开订单胶囊或点选订单气泡时，以订单 ID 选定自己的订单并咨询；选单与查询不自动申请退款/退货。
18. 同一个匿名 owner 的新会话可以查询该订单；其他 owner 看不到它，不映射到固定演示用户。
19. 用户按说明启动同版输入并执行代表性场景；技术验证、真实模型/页面结果和本人验收分别保留证据。

## Implementation Decisions

以下为用户授权由主 Agent 选择并记录的实施细节，尚未实现；验证发现现有契约要求不同应记录证据并调整，涉及产品范围变化则询问用户。

### 人数、兼容用量与候选采购

- 沿用既有正整数人数接口和菜谱基准人数。需求按人数线性缩放；g/ml 保留精确数值，pc 在同一兼容食材总需求汇总后向上取整，不采用银行家舍入、重量与枚数之间推测转换。
- 只转换 g/kg 与 ml/l 等同维度单位。食材 ID、单位维度及明确条件兼容的菜谱需求才能聚合；来源继续记在现有 requirement/contribution 内，直接商品明确购买件数另加，不创建第二套分组状态。
- 各菜的原始线性缩放需求保留在来源明细；pc 的整枚采购覆盖量不改写该明细或菜谱原始用量。
- 默认必需食材选中、pantry 不选；用户手动件数仍作为本次采购选择，少于所需时如实显示覆盖不足，不把选择减少当作足量采购。
- 每食材在可兼容可售规格上比较实际整包总价，不按单包价选。候选必须满足库存和明确条件。“价格相近”定义为不高于该食材最低可行总价的 105%，在此范围优先更少剩余，再以总价、SKU ID 作稳定排序。不承诺跨食材或全局最优。
- 整份方案的实际选购总价仍汇总所有选中食材、调料和直接商品，并与任务预算核对；食材候选之间的有限比较不冒充整份组合的全局最低价。
- 先交付单规格多包核算；供给适配票验证同食材其他规格和有限组合，不能为缺货推荐其他食材。数据不足时保留既有 unknown/供给预览，明确未能核算，不新增默认假包装。
- 代表性用量场景选番茄炒蛋和 fixture 中另一道共用番茄的菜品，具体第二道及数字在数据核查后写入票据。库存变化使用独立 Offer 场景，不删除目录，也不改原 V1 数据库。
- 清单刷新与确认沿用现有版本、有效期、预算、排除及购物车校验；只在新增行为缺口处修改，禁止复制这些约束形成新门控。

### 可乐比较

- 使用现有五款已明确品牌/包装的可乐 fixture；旧泛称 SKU 若缺某筛选事实，不参与要求该事实的比较，保留普通具名商品路径。
- 每件容量来自已核 metadata，销售包装总容量与整包件数区分；单位价显示为元/升（展示四舍五入到两位，排序计算不依赖展示值）。
- 聊天最多展示五个候选，使用现有候选引用与商品卡片/气泡。过滤条件进入当前会话已有条件及语义契约，不保留另一份前端权威候选状态。
- 品牌精确匹配已核品牌，容量指每件，件数指整包内件数，售价指一销售包装报价；条件修改后重查可售 Offer，用户选定才准备清单。
- 不新增独立比较页或比较管理面板；现有入口上下文和 SSE 保留。

### 跨会话记忆与历史方案

- 记忆是新增业务事实，按现有 owner 存储，四类 user/feedback/project/reference、来源 explicit/automatic 分别记录；不把任务或会话 State 复制造成记忆。
- 显式有效内容无自动到期，直到用户纠正/删除。自动提取默认 30 天有效期；订单/价格等引用查询业务源，不将记忆当成事实。
- 当前明确表达高于记忆，显式保存高于冲突自动提取；不强制旧排除覆盖当前本次明确例外。例外只作用于本次，除非用户明确要求修改长期记忆。
- 默认每轮最多召回五条相关记忆、合计 2000 字，召回长度与保存承诺分开；查询“记住了什么”可以读取完整有效列表，不能借召回上限删除显式内容。
- 回复完成后用现有后台执行机制提取，后台独立数据库事务；不为一次性整理引入调度平台。Dream 在有效自动条目达到 10 且距离上次整理 >=24 小时时触发；新保存变化后检查，不占最终回复主链路。
- 使用显式配置的较轻量 MEMORY_MODEL，调用现有 OpenAI-compatible 模型边界；不自动回退到主模型，也不把 missing/model failure 当作无新记忆。真实模型可用性需专职测试核查，外部不可用标记阻塞。
- Dream 只编辑自动条目及清理过期自动内容，显式内容不可被其删除；聊天显式修改操作可更新它们。记录后台失败，沿现有错误/Trace 机制保留原因，不新增宽泛吞错/重试。
- 历史方案摘要引用现有不可变方案快照与任务/订单 ID；复购创建本次任务/清单，默认仍执行必需/pantry 选择规则，旧勾选/加购授权不恢复。历史来源不足则必要澄清。

### 持久模拟订单与墨墨

- 下单由已有购物车结算交互独立触发，可可只加购，不把聊天确认升级为结算/支付授权。
- 采用现有同仓 SQLite，在本次 owner 下持久化订单及订单明细快照；Ceres 目录为商品事实源，订单保留购买时名称、SKU、数量、成交价。
- Mercury 查询改读本次统一订单事实，售后申请仍使用既有边界；不将当前 owner 回退成固定演示用户。初始化不得运行会删除活动数据库的旧 Mercury seed。
- 沿用两角色独立会话，墨墨只新增订单胶囊与绑定 ID 的订单选项，当前售后对象由会话管理；不自动跳转、不迁移导购消息。
- 查询与选单是只读业务，不提交退款/退货；明确诉求按现有售后执行契约验证，不新增重复确认。

## Testing Decisions

主 Agent 编写测试/修复并选择验证范围；所有测试命令，包括编译、TDD 红绿、行为脚本、模型探测与浏览器验收，均只由专职测试子 Agent 执行。测试子 Agent 不改源码、测试、文档、TASK 或 Git，不创建提交。生产数据禁止作为测试写入目标。

公共 seam 优先是已有 Guide HTTP/SSE、清单修订/会话恢复/确认 API、购物车 API、商品 read API，以及必要新增的订单/记忆聊天入口。确定性包装数学可通过现有公开模板/采购服务验证真实输入输出；不测试新私有函数或内部调用次数。

外部模型响应可在 provider 网络边界替换；内部业务、状态、供给、金额与加购使用真实服务及隔离 SQLite。离线行为正确不能证明模型理解/15秒速度或真实向量质量；这些另记真实采样。

既有测试参考：purchase selection、shopping workflow、template matcher、gap integrity/partial plan、snack selection、read tools、semantic constraints，以及 cart/confirmation。每票先新增一个行为红测，专职 tester 报告实际失败，再最小实现、绿测及相关回归；不一次写整套红测再写整套实现。

每次报告必须保存实际命令、cwd、解释器/环境、隔离数据目标、起止时间、退出码及原始关键输出。主 Agent 在 work/ 记录报告，不能由 tester 修改仓库文件。固定代表性用例各两独立运行（独立 owner/session/database），无需全目录扫描或恢复历史语义 A/B。

每票以固定 Git 基线到本票提交做两个只读审查，并把修复后的新增文件纳入复审。集成回归最后执行一次必要集合；若新失败/修改才重跑相关范围。人工检查由用户本人执行，其项目保持待验收。

## Out of Scope

PRD/简历/冻结 V1 plan 修改；自动整餐、关联推荐、全局最优、营养、购物车补齐、真实支付履约/库存、跨设备账号、独立记忆页/比较页、自动跨角色接管/消息迁移、转人工扩展、全105菜验收、无依据兜底/重试/异常捕获、新架构或无调用方抽象。

## Further Notes

实际工作目录为现有 Ceres，路径阻塞已解除。Ceres 有大量已有未提交 V1 有效改动，不能整仓暂存为某张 V2 票；已记录继承输入与原 Git dirty 状态，并隔离本票变动。V1 原任务状态与失败证据必须保留，不宣称整体完成。
