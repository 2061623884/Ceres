# Ceres 下一阶段 Agent 体验实施规格

版本：2026-10-06-v2。产品范围来自本轮已确认讨论，以 V3 已开发完成为前提。本文按 /to-spec 整理；用户已授权按 implement-spec 执行八票，测试接缝与拆票粒度已确认。推进与实施状态见实施总 TASK 及各票。

流程参考：[预期 Agent 流程](../../work/ceres-next-discussion/expected-agent.mmd)。任务入口：[实施总 TASK](../../tasks/ceres-next-agent-experience.md)。历史拆票参考：[票据草案](../../work/ceres-next-discussion/ticket-breakdown.md)。

## Problem Statement

用户提出“来点零食”时，期望先选择类型，再选具体商品；直接推某一款商品会过早收窄需求。多个候选跨越不同类型时，也需要通过气泡表达选择，而不是反复输入文字。当前讨论还要求改善售后表达，让一次“先退后买”的诉求在两个 Agent 间完整接续。

产品需要一个简单的主页专题入口，展示对应限定成品商品，形成活动氛围。架构上希望试点可可内部的 Kev 能力路由，让参数明确的工作交给 workflow，并精简、模块化 Prompt。上述改进须有固定用例、原始记录和前后对照，支撑产品演示与简历叙述。

## Solution

首轮围绕零食和饮品提供分类与筛选气泡：宽泛需求先问类型；跨类型候选先概览、再分类；同类候选直接展示商品并提供有依据的筛选选项。点选后保留有效条件，沿同一采购诉求继续，最终仍由用户确认加购。

沿用 Kev-4B，首先在可可内部试点品类探索、采购与修改、事实问答、普通聊天四类能力路由，按分支组合必要 Prompt、工具与事实。复杂自由文字保留主模型理解，参数已齐全的操作由确定性 workflow 完成。Prompt 先模块化，再逐模块精简。

打通购买、独立模拟结算、售后申请提交、用户选择继续采购、可可选购替代商品的代表链路。两个角色均用简短自然的中文说明结果与下一步。主页专题复用现有卡片，直接进入可可展示介绍及限定成品，选购复用已有流程。

每个增量同步形成行为验收与证据。先确保体验、事实及授权正确，再报告主模型调用、Token 和响应耗时的实际变化。

## User Stories

1. 作为选购用户，我希望说“来点零食”后先选择零食类型，以便找到符合兴趣的商品。
2. 作为选购用户，我希望宽泛饮品需求先得到类型选项，以便缩小选购范围。
3. 作为选购用户，我希望候选跨越不同类型时先看到概览和分类气泡，以便理解有哪些选择。
4. 作为选购用户，我希望同类多个商品直接展示，以便及时比较具体商品。
5. 作为选购用户，我希望按口味、品牌或规格筛选同类候选，以便表达偏好。
6. 作为选购用户，我希望气泡仅提供当前供给支持的选项，以便选择后得到对应商品。
7. 作为选购用户，我希望气泡回答保留已经明确的预算、数量等条件，以便不用重复描述。
8. 作为选购用户，我希望仍可输入自由文字回答，以便表达气泡未覆盖的需求。
9. 作为选购用户，我希望每个气泡绑定对应问题，以便同名选项也能正确推进当前诉求。
10. 作为选购用户，我希望选择类型与筛选条件后仍能明确确认具体商品，以便掌握采购决定。
11. 作为选购用户，我希望加购遵循已有确认规则，以便选择气泡不会直接写入购物车。
12. 作为采购用户，我希望参数已明确的操作直接完成，以便减少重复理解与等待。
13. 作为采购用户，我希望复杂、多目标或修订表达继续被完整理解，以便 workflow 不丢失语义。
14. 作为可可用户，我希望不同诉求进入合适能力，以便得到与当前问题相关的处理。
15. 作为咨询用户，我希望商品或政策回答依据对应事实来源，以便核对答案。
16. 作为聊天用户，我希望普通闲聊得到简短自然回应，以便不会无故创建采购任务。
17. 作为两角色用户，我希望一般咨询与具体订单业务遵循既有服务边界，以便切换符合实际需要。
18. 作为两角色用户，我希望由自己选择服务切换，以便掌握当前服务。
19. 作为先退后买的用户，我希望墨墨提交售后申请后能继续选购，以便一次表达可以完整处理。
20. 作为先退后买的用户，我希望交接保留明确对象、剩余诉求和有效条件，以便不用重输。
21. 作为订单用户，我希望目标角色重新查询正确订单与事实，以便旧对话不覆盖当前状态。
22. 作为售后用户，我希望准确区分申请提交和退款到账、退货完成，以便了解实际进度。
23. 作为售后失败的用户，我希望先了解失败结果再决定是否继续采购，以便保留自己的选择。
24. 作为先退后买的用户，我希望已完成步骤不重复执行，以便一次交接不会重复提交申请。
25. 作为售后用户，我希望回复简短、自然，并说明下一步，以便容易理解并继续操作。
26. 作为售后用户，我希望必要政策依据仍清楚可读，以便自然表达不丢失来源与条件。
27. 作为主页用户，我希望从现有卡片进入专题，以便发现活动商品。
28. 作为活动用户，我希望看到简短专题介绍和对应限定商品，以便感受到活动氛围。
29. 作为活动用户，我希望沙拉、拼盘按成品展示，以便直接选择现成商品。
30. 作为活动用户，我希望商品选购接入已有流程，以便沿用熟悉的比较和确认方式。
31. 作为产品负责人，我希望必要时补充最少的模拟商品及供给，以便真实覆盖已确认测试场景。
32. 作为产品负责人，我希望商品、供给、索引与评测版本可定位，以便复现实验并解释差异。
33. 作为产品负责人，我希望先模块化再精简 Prompt，以便保留规则并定位改动效果。
34. 作为产品负责人，我希望前后对照固定输入、模型、数据和其他条件，以便结论对应实际改动。
35. 作为产品负责人，我希望记录实际 Prompt、逐轮输出、业务结果、错误与耗时，以便复核成功和失败。
36. 作为产品负责人，我希望新留出独立于开发与回归，以便避免把调参案例当作独立验证。
37. 作为求职者，我希望用用户问题、产品闭环、架构取舍和测评证据说明项目，以便简历与实际成果一致。

## Implementation Decisions

### 模块与职责

- 沿用现有聊天、导购回合、确定性业务执行、商品供给、服务交接、售后、前端聊天与评测模块，不建立通用多 Agent 编排平台。
- 首轮分类覆盖零食与饮品。具体细类和筛选维度根据商品属性及供给确定；类型差异决定是否继续分类，候选数量不单独决定。
- 前端保留当前问题与选项身份，点击回传其语义及对应问题，不能仅依赖显示文案推断；自由文字路径保留。按现有回合与版本契约承接选项。
- 分类与筛选选项不冒充具体商品引用。明确选品后复用清单及确认加购，已结束的问题不继续作为有效澄清。
- 必要的契约增量限于选项回答、内部能力判断、代表链路承接和专题上下文，字段在实现时沿现有定义、调用方和测试确定。

### 能力路由与 workflow

- 外层服务归属路由沿用 V3；可可内部新增有界四类能力判断。两类判断各自保留选择、准则版本与实际记录。
- 内部 Kev 不生成自由业务参数、不虚构商品或订单、不授权业务写入，也不改变服务角色。
- 有效结构化输入及参数齐全的操作直接进入对应 workflow；复杂自由文字仍由主模型理解与参数提取。记录实际省去的是哪个模型调用阶段。
- 能力分支仅选用当前相关 Prompt、工具和上下文，不新增无调用方的配置、推测性重试、主模型替代路由或概率阈值。

### Prompt 与表达

- 先分别组织公共表达规则、角色规则、当前能力规则与本轮必要事实，保留行为语义；在模块化版本验收后逐模块精简。
- 协议、角色边界、事实来源及确认规则不得因缩短而退步。可可与墨墨均采用简短自然的中文，先说明结果及下一步。
- 售后明确诉求与业务授权沿用现有语义，不因角色切换额外授予执行权，也不为明确退货请求新增重复确认。
- 政策回答保留来源和适用条件，用易读表达呈现必要依据，不把内部检索叙述当作主要回复内容。

### 代表链路与活动

- 购买确认加购后，由独立模拟结算生成订单；墨墨处理售后申请，再由用户选择进入可可处理剩余采购诉求。交接保留有效条件、明确对象与步骤结果，目标服务重新读取事实。
- 售后申请提交成功仅代表对应申请状态；失败先解释并暂停，继续采购也保留失败结果。已完成步骤不重复执行。
- 仅实现这一有界代表链路，不建立任务队列或通用顺序执行器。
- 主页复用现有活动卡片，直接进入可可；专题关联介绍及限定成品商品清单。名称、文案和具体商品在已给参考及供给条件内确定。
- 专题选购继续受对应商品范围与既有确认规则约束。若展示活动期限或优惠，信息必须来自活动数据。

### 商品与证据

- 必要时允许补充支撑已确认场景的最小模拟商品及对应供给，沿既有导入和索引流程处理。各票登记自己需要的供给，主会话协调共享数据与契约的修改归属。
- 记录代码及未提交源码、商品/供给、索引、模型、用例和实际 Prompt 的适用版本，保留逐轮原始响应、业务状态、判断、来源、错误和耗时。
- 对照使用同一批冻结业务数据，避免将商品扩充的效果归因于路由或 Prompt。接口可获得 Token 时记录用量，不把缺失用量当作零。
- V3 冻结版本用于既有能力整体对照；路由或 Prompt 的单变量比较另使用业务已就绪的阶段基线，并固定其他条件。

## Testing Decisions

主要测试接缝是现有公开聊天接口的一条多轮会话旅程，涵盖回合、清单确认、角色交接及可查询业务结果。分类气泡与主页入口补充现有前端的实际点击验证。复用已有接口和执行器，不新增测试专用产品 API 或通用测试框架。

- 好的测试断言用户可见回复、结构化选项、选择后的条件、实际商品/清单/购物车/订单/申请结果及授权边界；不锁定内部函数数量、节点命名或 Prompt 文本布局。
- 参考现有公开接口的导购用例、角色路由与切换生命周期用例、订单与售后集成用例、Trace/多轮执行器记录约定。旧结论不充当新版本执行结果。
- 每票携带代表行为与必要反例：宽泛需求、跨类型候选、同类筛选、文字回答、确认边界；四类能力及结构化直达；正确订单续接、申请失败暂停与继续、已完成步骤不重放；活动范围与成品选购。
- 关键违规为零：未授权写入、错误订单操作、未选择的服务切换、重复执行完成步骤，以及编造商品或政策事实。业务体验达标后比较调用次数、Token、阶段耗时与完整回复耗时。
- 语气自然度单独人工审读实际对话，检查简短、易读、状态准确和下一步清楚；不以字符串完全相等代替表达验收。
- 确定性测试、受控模型接口、真实 Kev/角色主模型采样、前端端到端与人工审读分别报告。真实模型判断及性能以实际调用记录为准。
- 沿用 V3 公开回归用例，新增四条场景的最小增量集。开发、回归与新留出按场景分组，等价改写不跨集合；已用于开发或反复查看的案例不作为新的独立留出。
- 候选冻结后执行新留出，保留失败；不得根据失败修改同一候选后仍宣称该留出独立。样本量与冷启动条件随耗时结论保留。
- 每步固定其适用版本与实际改动变量；性能、通过率改善值由结果决定，不预设数字。执行测试及审查遵循项目既有分工。

## Out of Scope

- 核验 V3 是否已完成，或改变其任务状态与历史证据。
- 真实支付、真实商超库存、履约、真实退款到账；价格、库存、配送与订单仍为模拟数据。
- 活动评论、投票、晒单、社交关系、签到、会员或营销运营平台。
- 将活动沙拉和拼盘转成食材采购、营养规划或整餐优化。
- 全品类扩展、完整品类树平台、通用跨 Agent 编排、自动角色跳转。
- 换掉已选定 Kev 模型，或无依据增加兼容层、配置开关、兜底与重试。
- 改写简历、修改旧阶段任务状态或核验 V3 完成度。

## Further Notes

推进次序已确认：分类气泡与 workflow → 可可内部 Kev 与 Prompt → 双 Agent 闭环与表达 → 主页专题；每步同步形成评测证据。票据的技术阻塞与该推进顺序分别表达，独立功能不因排期被伪造为技术依赖。

领域概念沿用根词汇表；具体细类、活动商品和最小字段由执行者依据供给与既有调用链确定。第一版不预设完整数据量和统计泛化结论。

简历以用户需求与产品闭环为主，以能力路由、workflow 分工、Prompt 组织和评测作为支撑。只使用对应版本的实际结果说明成功率或开销变化，保留失败及样本范围。
