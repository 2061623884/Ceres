# Ceres V3 实施规格

版本：2026-10-06-v1。产品来源为 [V3 讨论稿](../../PROJECT-v3.md) 中 Q1–Q23；用户已确认整体范围并授权形成规格、拆票和执行准备。当前状态与负责人见 [V3 总 TASK](../../tasks/ceres-v3.md)，本规格不维护第二套进度。

## Problem Statement

同一用户在可可和墨墨中使用不同业务服务，当前没有跨角色原话续接。按关键词切换会把购物中的一般政策问题误当成售后，用户也可能需要重复输入。可可尚无政策读取入口，墨墨的一般咨询被强制选订单挡住。用户希望采用已选定的 Kev-4B 做保守的上下文路由，并用可复核评测支持最后的 Prompt 精简。

## Solution

按 V2 成功规划，继承购买、记忆、持久模拟订单与已有售后能力。每条新用户消息先由 Kev 结合当前角色、明确对象和必要相关对话作三类服务判断；当前角色能处理则继续，明确需另一角色才建议切换，仍不明确则原聊天澄清。切换由用户选择，目标角色携原话续接并重新查询业务事实。一次打开最多自动提示一次，固定手动入口持续可用。

第一批知识覆盖共用的模拟门店退换货、配送与售后流程。一般政策咨询无需先选订单，回答附适用条件与政策来源。售后本身不扩展为 V3 开发重点。业务完成后冻结 V3 基线，再改良 Prompt 并比较结果。

## User Stories

1. 作为选购用户，我希望普通采购诉求继续由可可承接，避免无关切换。
2. 作为购物中的用户，我希望问“不喜欢能退吗”时由可可回答一般政策，继续选购。
3. 作为咨询用户，我希望知道政策条件和来源，避免把一般规则误认为我的订单资格。
4. 作为墨墨用户，我希望没选订单也能咨询一般政策。
5. 作为订单用户，我希望具体查询、资格判断和操作基于本人的明确订单。
6. 作为使用指代的用户，我希望“取消一下”结合清单或订单上下文理解。
7. 作为表达仍含糊的用户，我希望在原聊天澄清对象，而非被擅自切换。
8. 作为改变话题的用户，我希望本轮明确的新诉求优先于旧话题。
9. 作为需要另一角色的用户，我希望先看到切换询问，自行决定是否进入。
10. 作为接受切换的用户，我希望目标角色直接处理原问题，无需重输。
11. 作为已有两角色会话的用户，我希望两边各保留聊天与业务进度。
12. 作为拒绝切换的用户，我希望继续当前服务，并能使用固定切换入口。
13. 作为反复提出跨服务问题的用户，我希望本次打开不重复出现自动提示。
14. 作为来回切换角色的用户，我希望切换本身不恢复自动提示次数。
15. 作为重新进入聊天的用户，我希望新的打开周期可再次出现必要提示。
16. 作为主动切换的用户，我希望明确未处理的跨服务诉求可以续接。
17. 作为单纯切换角色的用户，我希望恢复目标会话，不重发已处理旧消息。
18. 作为交接订单 A 的用户，我希望目标角色查询 A，避免静默沿用旧会话订单 B。
19. 作为闲聊用户，我希望可可回应问候和简单生活感受，不自动创建采购任务。
20. 作为表达吃饭或采购需求的用户，我希望自然进入导购；持续偏离业务时得到简短范围说明。
21. 作为路由服务暂不可用时的用户，我希望得到明确提示，并能继续当前角色业务或手动切换。
22. 作为等待回复的用户，我希望常规路由新增等待 P95 ≤1 秒，完整回复以 ≤15 秒为目标。
23. 作为产品负责人，我希望模型、数据、用例、Prompt 与执行证据有固定版本，失败不被记作成功。
24. 作为产品负责人，我希望 Prompt 精简相对业务完成后的 V3 基线比较，关键业务行为不能退步。

## Implementation Decisions

### 既有能力与模型职责

统一匿名 owner、持久模拟订单、两角色现有业务执行和导购内部回合职责均沿用 V2。业务服务路由位于角色业务处理之前，不替代导购内部语义理解、工具选择和确定性执行。Jev 只借鉴入口判断思路，不扩展其他判断节点或通用多 Agent 框架。Kev 已选定，不设置与主模型对照后决定采用的门槛；两角色主聊天模型保留原职责。

固定 Kev 源码 `fe64b1274ea7f80d4095866df90666abb03e9cf6`、checkpoint `139fdd94f1b6a6ad80cc15e08fcb99cac885a101`、Qwen/Qwen3.5-4B-Base revision `1001bb4d826a52d1f399e183466143f4da7b741b`。Amax 使用物理 GPU 1，UUID `GPU-5165b827-1b01-e6f0-d147-38e565ee823f`；复核占用后使用独立环境与当前卡可用的 FP32 路径。下载校验、加载、API、中文采样和速度分别记录，不能互相代替。

独立服务初始绑定 Amax `127.0.0.1:8009`。执行 01 时核实实际缓存位置，避免旧启动脚本读错缓存；03 再核实 Ceres 后端运行主机与实际可达调用链。现有服务地址配置只覆盖真实调用需要，不新增多提供商切换或主模型路由兜底。中文质量、显存与延迟尚待实测，未达标保留失败和阻塞，不更换既定模型或宣称通过。

### 上下文与闭合判断契约

输入包括本轮原话、当前角色、owner 下的角色会话、当前选中或明确指向的商品／订单、必要近期相关对话，以及正在等待回答的澄清／切换问题。复用已有上下文与聊天读取能力，不复制全部历史；聊天只是理解来源，业务事实仍重新读取。本轮明确新诉求优先。

调用官方 `/v1/systemone`，给定 `stay_current`、`suggest_switch`、`clarify` 三个选项及已确认的保守准则，记录官方 choice 与概率。初始应用使用该闭合 choice，不凭空增加概率阈值；在开发案例中改进输入和准则并固定版本，只有具体误判证据需要时才校准额外判据。概率不直接当作可靠业务置信度。

角色回合新增可观察的服务路由结果，至少关联源 request_id、当前角色、三类决定、需要时的目标角色与交接标识，以及可展示的提示方式。原话／对象／相关对话由应用形成交接上下文，不能由 Kev 虚构对象或生成聊天答案。正常角色业务的响应字段与版本检查沿用原接口；可可和墨墨各自现有 SSE 封装保留，不为本任务重写整个传输协议。

### 角色边界与呈现

可可负责选购、比较、清单和采购安排；墨墨负责明确订单查询、实际资格与售后操作。一般退换货、退款、配送政策及正常闲聊可由当前角色处理。明确跨服务诉求先建议切换，未经选择不切换角色、不执行另一角色业务。对象仍不明时在原聊天澄清，不能把含糊概率包装成切换建议。

用户接受建议后，以原话和必要交接上下文在目标角色发起对应回合；目标角色重新检查 owner 与对象事实，明确指向订单 A 时不得沿用旧订单 B。切换只选择服务，不代替加购或售后原有业务确认。两角色会话分别保留，不建设全量历史同步或额外跨设备会话系统。

自动提示次数属于“一次打开聊天”的应用状态，两角色共用。第一次实际展示即消耗，接受、拒绝及来回切换均不恢复；结束本次打开并重新进入才创建新周期。最小 demo 与后续 Cursor 界面使用同一进入／退出聊天的生命周期约定，不另把页面刷新列为重置条件。该状态不作为用户永久偏好，不新增持久用户偏好表。后台每条消息仍判断；额度耗尽时只说明必要能力边界与固定入口，不能重复以聊天追问方式弹出同一自动切换询问。

固定入口的主动选择本身不再弹确认：存在明确、尚未处理且归目标角色的诉求时续接，否则只恢复目标会话。新诉求或已处理结果使旧待交接内容失效，不能任意重放历史消息。交接与目标处理关联源请求标识，重复点击／重复提交复用已有回执能力；目标入口缺少回执时只补交接所需去重，不顺带重构普通售后调用。消费状态与实际处理结果必须对应，未成功不能写成已完成。

### 模型不可用与等待

外部 Kev 网络失败、超时或不符合当前接口契约的响应，在路由边界转换为可观察的不可用状态，保留原始错误原因与时长。提示自动路由暂不可用，当前角色只处理自身业务，固定入口可用。该轮计为路由失败，不静默记成 `stay_current` 成功，也不由主模型接替路由判断。

03 根据 01 的实测和现有回合预算固定有界等待，记录所用值；1 秒是路由新增阶段的 P95 目标，不直接等同于每次请求的硬超时。无法满足时如实阻塞性能验收，禁止用无限等待、屏蔽失败或更换模型掩盖问题。本轮不预设重试、异常兼容或额外恢复框架。

### 政策读取与闲聊

两角色读取同一模拟门店政策事实源，返回可追溯的 policy_id／标题与适用条件。政策初始化应独立于必须先创建售后会话的隐含时序，使可可先问政策也能读取。优先复用现有政策表与检索；只依据漏召回和错答修改必要检索行为，不预建另一套向量知识库或商品知识百科。

墨墨未选单的一般咨询不能只是删除 API 选单提示后暴露全量订单工具：该入口仅开放政策读取与一般回答，明确订单业务仍先选单；已选单场景也不得因一般咨询自动提交申请。可可政策读取是只读能力，不执行订单动作。不命中或缺少条件时说明已有依据的范围，必要时询问缺失条件，不编造商家承诺。

问候及简单生活感受正常回应；用户表达吃饭或采购需求时进入既有导购，持续偏离业务时简短说明范围，不把每次闲聊创建成购买任务。第一批不包含商品保存、食用方法等知识扩展。

### Prompt 改良与证据

先完成核心业务并冻结未精简的 V3 基线；将公共业务边界、角色规则、政策依据和协议约束按现有 Prompt 组合入口整理，只拆实际调用需要的部分。固定用例、数据与模型后改变明确的优化变量，比较正确性、依据、实际 Prompt 长度及耗时。不能通过删除协议或业务约束缩短文本，关键业务行为不能退步。

## Testing Decisions

采用已有公共角色聊天 API/SSE、会话/选单 API 与实际业务状态作为最高测试入口。已有订单 owner 隔离和回合回执测试是先例；模型边界注入确定响应，以验证继续、建议、澄清和不可用行为，不镜像内部函数实现。涉及新业务行为时在上述入口先写失败断言，再作最小实现与必要回归。前端只做用户已要求的最小 demo 和可交给 Cursor 的接口约定，正式 UI 实现不纳入本会话源码范围。

固定核心覆盖为 [18 个案例](../../work/ceres-v3-discussion/evaluation-plan.md)：R01–R10、H01–H06、F01、P01。政策、owner 隔离、不同订单交接、重复提交及用户确认以外部状态断言补充，不改变核心业务预期。用例实际数据与版本在对应票执行时建立，冻结后不可按采样结果改写预期来宣称通过。

评测记录包括源码 commit 与未提交源码冻结、供给/订单/政策、用例、Kev/基础模型/主模型、Prompt/准则版本、实际上下文、原始 choice/概率、应用决定、回复与业务状态、失败原因和逐轮耗时。公开核心用例属于开发／回归，留出集按场景组独立构建，近似改写不能跨集。初版业务断言与人工复核，含义待定输入不计通过率；模型调用失败不得剔除成正确答案。

路由新增等待从新增路由上下文准备开始，到 Kev 响应解析及服务决定可用结束，使用单调时钟；已经属于原业务处理的阶段不重复计入。报告正常输入逐轮时长和样本量，按 nearest-rank（排序后第 ceil(0.95*n) 个）计算 P95，冷启动单列。完整后台回复从聊天请求接收计至 `turn.completed`；有页面证据时另记从发送到最终呈现的用户等待，二者不混用。超时和失败单列，不能靠排除失败宣称达标；模型加载探查的长等待预算不沿用为正式回合预算。

固定核心用例全部通过、关键违规为零；性能检验路由 P95 ≤1 秒和完整回复 ≤15 秒目标。05 可在业务通过并保留实际性能不足后完成基线交付，使 06 可以改良；性能不因此变成通过，07 仍需验证最终同版目标。真实模型、受控验证、页面与用户本人验收分别记录，不能用其中一种代替另一种。

每票审查 Standards 与 Spec 两轴，修复有效发现并复验。按本项目规则运行与改动相关的验证；规格／票据准备不运行业务全量测试，最终实现作相关模块完整回归。局部提交只包含本票变化，不推送、不混入继承 V2 dirty。

## Out of Scope

不重新决定 Kev 是否采用，不替换两角色主聊天模型，不建设更多 Jev 判断节点、通用多 Agent 消息总线或完整跨服务编排。售后功能扩展、商品知识百科、前端视觉完善、跨设备账号、全历史同步、真实支付与履约均不在核心范围。价格、库存、配送和订单继续为模拟数据。既有 V2 TASK 的实际状态不因规划前提而改写。

“先退后买”是独立探索：申请提交成功后可推进采购，不等待到账；失败暂停、解释并询问是否继续，用户继续也保留失败。每次服务切换仍遵守选择与提示限制。探索失败不阻塞核心，不能将失败探索写成业务成功。
