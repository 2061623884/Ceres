# 05 category prompt A/B interpretation

The comparison is one real-model sample per case and arm. Both arms used the same lexical fixtures/index construction, Qwen semantic model, and controlled Kev capability route. The four tester-launched samples ran serially; unrelated model traffic was not observable. Full sanitized requests, responses, options, and usage remain in the case JSON files under `before/` and `after-category-only/`.

The controlled `snack_type_first` case kept the same public result: a product-type question for chips or crackers, with no cards, plan, or cart change. Semantic calls stayed at two, while prompt tokens changed from 6,454 to 5,876. Separately, the controlled public-request test measured the first outbound body at 15,385 bytes on the frozen baseline and 14,034 bytes on the final candidate, a 1,351-byte (8.78%) reduction. This supports a prompt-size reduction for this fixed request, not a general quality or latency claim.

The `same_category_cola_filter` case showed one Coke card before the filter, so it did not exercise a multi-candidate comparison. Both arms later retained the one-item plan and left the cart unchanged. The semantic content of the price-filter response differed: the baseline incorrectly treated the request for items under ¥1 as an attempted change to the existing small-package plan; the candidate said no item under ¥1 was found. Preserve the baseline response as a semantic failure. Do not attribute the candidate wording improvement to this ticket: the Coke prompt module was unchanged, and the first two captured request bodies are byte-identical across arms. The response difference is an uncontrolled single-sample variation.

The Coke case used five semantic calls before and six after; prompt tokens increased from 29,002 to 32,408. The added final-turn call is visible in the captured range `[4, 6]`. The end state alone (zero cards after filtering and unchanged cart) does not establish that both answers interpreted the price constraint correctly.

Evidence: `before/run-summary.txt`, `after-category-only/run-summary.txt`, `canonical-capture-metrics.txt`, `green/controlled-final-candidate-meter.txt`, and the corresponding per-case JSON files. The canonical byte/hash metrics are deterministic re-serializations of captured request fields; the controlled body-meter test records actual `request.content` bytes.
