# 05 原始失败与修正

原始 `core-001`、真实 v1/v2 结果均保留，不回写通过。业务数据、固定原话和标签、Kev 权重、两角色主模型及参数均未重新选择。

- 受控 R01 的语义边界已给出 quantity=2，但新目标经过 GoalCandidate 后丢失，最终清单为 1。最小生产修正将明确产品件数经 Goal.quantity 传到 Mutation；未指定数量保留默认行为。core-002 的 R01/R08 门槛 2 项及核心 16 节点加 2 Goal 回归通过。
- 原 v1 R06 没有准备固定案例中的清单移除问句；v2 补齐后仍两次 clarify。实际上文已明确采购清单，未选中商品不妨碍确定服务。独立 Spec 诊断要求先判断服务归属，将可可内部尚需澄清的商品/动作留在业务回合。准则升级为 ceres-service-v3.2；不造对象、不改标签、不增加代码层强制判定或阈值。
- 鸡蛋具名变体未指包装枚数；v1 强制 6 枚装的断言没有原话依据。修正版允许冻结供给中两种现有鲜蛋 SKU，且件数 1、实际成分/报价/可售库存正确。v2 R01 真实模型给出 quantity=2，实际清单也为 2；新增的 user_quantity==2 断言混淆初始产品需求与后续共享行手动覆盖。独立 Spec 核对 build_product_plan/apply_row_quantity/_collapse 后删除该断言，保留 SKU、实际件数和报价库存断言。旧 false 结果不修改。
- v1 只捕获 Ceres httpx，漏掉当前 OpenAI 3.19.2 的 httpx2 请求；v2 覆盖 SDK 的公开 DefaultHttpxClient，已记录墨墨实际请求、响应和 usage。公开类只在 opt-in 采样函数中导入，普通收集不依赖新 SDK 符号；真实测量适用记录的 3.19.2 环境，不宣称跨版本测量。
- Standards 要求请求异常也有原始逐例回执：采样器在 finally 写入并重抛原异常；分析器对缺失生产路由计时和未完成组保留失败，不排除后宣称 Q20 通过。修正版回执摘要按实际 write_bytes 字节计算，v1 的换行摘要问题另有审计。

新版本执行与两轴复审另记；这些修正说明本身不构成通过证据。

v4 的输出预算已消除 R01 截断，两次主模型响应均 finish_reason=stop。第一轮 category/explore + compare 返回实际商品卡，没有计划。独立 Spec 再核对 PROJECT-v3 Q13、固定 R01 标签及 V2 可乐专规则，确认首轮强制 plan 的断言无依据；它要求跳过用户选款。v5 改为真实多轮验收：首轮只读及路由、用户明确选实际卡片并要两瓶、随后计划和当前事实均验证，选款回合单独计时。原 v4 失败和字节证据保留，不以删除计划断言冒充采购完成；生产 Prompt 与品类规则不改。

v5 五份真实角色回执及 R01 多轮旅程通过。Standards 发现选款回合在解析 SSE 前未记录原始响应；v6 仅调整观察记录顺序：先保存收到的 HTTP/SSE/时延再解析，在发送选款请求前保存实际请求与卡片。原异常继续向外传播，不改断言、生产源码、Prompt 或模型，也不重新采样已通过的角色组。真实结果仍标注 v5 源版本，兼容性与受控失败探针另行记录，不能将探针冒充模型通过。

v3 的 22 条真实路由已通过；R01 又发生独立主模型失败：HTTP 200 的内容为 null，finish_reason=length，1536 个 completion tokens 全为 reasoning，服务正确返回 MODEL_OUTPUT_TRUNCATED、saved=false、无计划。经独立诊断，v4 只将既有运行配置预算提高至 3072，权重、主 Prompt、协议和业务保持原版；不复制包含凭据的 .env，仅冻结非敏感设置及实际 payload。更多预算不保证成功，原失败与可能增加的等待保留。分析器同时要求五条指定角色回执及 H01 确认回合的完整计时，防止仅现存成功记录误报 Q20。
