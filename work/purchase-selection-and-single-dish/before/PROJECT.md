# Ceres 项目总览

更新于 2026-10-04。产品定义以 [PRD](prd.md) 为准；本文记录当前阶段目标、改进方向和依赖，任务状态及证据以 `tasks/` 为准。

## 产品目标

帮助用户把模糊购物需求转化为可执行的购买方案，降低搜索、比较和商品组合的成本。

PRD 的两个 P0 场景仍是：

- **购买任务规划**：从用户想完成的事情出发，形成实际可购买的商品组合。
- **品类内选购**：根据预算、用途、规格等条件缩小候选范围，帮助用户选择商品。

当前阶段以单道菜采购为重点，同时覆盖基础商品选购。模型理解用户表达，商品系统提供价格、库存等事实，用户明确确认后才加购。导购 V1 止于确认加购；购物车补齐属于 P1，结算、支付、配送履约和售后沿用独立流程。长期画像不作为当前阶段的必要前提。

购买任务也包含直接商品选购，例如买零食、饮料或果汁，不需要先转换成菜品。基础商品选购作为并行演示路径，纳入本阶段必验范围。

## 当前阶段目标

**在有限、明确的模拟商品供给中，稳定完成单道菜的推荐或点名采购，以及基础零食、饮品选购闭环，形成可反复演示、能用证据说明能力和局限的导购 MVP。**

面向自己准备晚饭的用户，每次围绕一道菜推进：

需求表达 → 必要澄清 → 主推一道菜并说明理由，或接受用户点名 → 匹配可售商品 → 采购清单及用户勾选 → 修改与重新校验 → 用户明确确认加购。

用户可以继续提出下一道菜并追加到清单。当前不要求系统自动安排完整一餐，也不判断菜与菜之间的搭配、营养或推荐关联。

直接商品选购限定在本阶段约定的供给和用例中：用户点名商品时检索相应真实候选；只点名品类或表达“喝点甜的”等消费偏好时，主推一款符合需求的商品并说明理由，确有影响选择的歧义才澄清。用户点名或选定具体商品后生成采购清单，明确确认后加购。无符合需求的供给时明确说明，不擅自用其他品类替代。完整品类筛选和多 SKU 比较仍单独安排。

偏好匹配以经核对的商品名称、说明或标签中的明确描述为依据；`original/zero` 糖类型不直接等于甜度依据。本阶段不扩展定量甜度或糖含量筛选。资料不足时说明无法核查该偏好，允许用户进一步明确商品方向；澄清后仍无可核查候选就走无匹配出口。成功推荐与资料不足的用例分别验证，资料不足的正确退出不代替成功选购验证。

当前阶段不扩展人数换算，不以人数变化作为验收维度；沿用菜谱基准用量，不把默认用量表述为用户明确提供的信息。制作难度和烹饪时长也不作为本阶段选菜或验收条件。

价格、库存和配送为模拟数据，见 [bootstrap 数据说明](backend/app/api/bootstrap.py)。演示结果不代表真实商超成交、履约或真实用户决策效率已经改善。

## 本阶段业务规则

- **推荐**：菜品需求主推一道菜；基础商品需求主推一款商品。根据已生效的预算、当前会话明确表达的忌口和可核查供给说明理由；用户不满意时可以换。不编造未接入的偏好、制作时长、难度或口味依据。
- **采购选择**：沿用菜谱中的行角色；必需食材默认勾选，油盐等 `pantry` 项默认不勾选，用户决定本次实际购买哪些。未勾选不代表系统已经确认家里有该商品。选择、金额、后端清单快照和确认结果必须一致。
- **供给不足**：对本阶段菜品采购，先展示可售商品和缺项说明，作为供给预览；不创建或改写采购清单，不执行加购。等待用户决定调整目标、继续采购可售部分或退出，再按其明确选择重新校验；原有清单在决定前保留。
- **商品无匹配供给**：说明本次检索没有符合商品、品类或明确条件的可售候选，不生成无关商品清单，不主动推荐其他品类。用户主动调整目标后再检索，决定前保留已有清单。
- **追加与修改**：用户明确追加另一道菜或一款商品时保留已有分组；同一商品的数量按各分组贡献汇总。已有可编辑清单时，新购买目标未说明追加还是替换，应先确认关系，决定前保留原清单。已有单道整单换和按分组删除与多道清单中的局部替换不同；后者当前不能作为已具备能力宣传。
- **确认**：选择菜品或商品、生成清单和确认加购是不同动作。普通“好的”“嗯”等回应不得自动授权加购；购物车结果必须对应用户最终确认的采购选择。

领域术语见 [GLOSSARY](GLOSSARY.md)。

## 当前事实与改进顺序

已存在菜品检索、商品匹配、分组清单、追加和确认加购实现；这些代码能力不等于当前版本已经完整验收。现有语义交付和商品扩充交付仍以各自 TASK 的待验收状态为准。

直接商品采购有独立路由和计划准备实现。2026-10-04 按用户限定的“展示匹配商品”案例，已在当前运行库补入两项模拟零食，并以相同源码、模型和索引、独立 owner／会话重复两次通过“来点零食 → 展示匹配商品 → 就第一个 → 生成清单 → 普通好的不加购 → 明确点击确认加购”。本例展示两项候选供用户选定，只证明该有限供给下的闭环；单款主推与推荐理由、结构化筛选、多 SKU 比较及其他品类仍待验证。“甜的”没有结构化口味筛选字段；其他具名购买路径的首候选绑定仍需单独核对。实现与限定证据见 [零食 TASK](tasks/snack-selection.md)、[商品路由](backend/app/agent/goal_router.py)及 [语义规则](backend/app/prompts/semantic.py)。

当前 [商品 fixture](data/fixtures/demo-products.json)及开发库已有正式 `snack` 类的原味薯片70克袋装、苏打饼干100克盒装，分别具有 ¥5.90／30 包、¥6.90／20 盒的模拟门店 Offer；本轮只新增这两项，旧商品与 Offer 保留。可乐、绿茶饮料、苏打水等已有供给不代表饮品闭环已验收，fixture 仍没有已核对的果汁商品；花生米条目保留烹饪用途。部分可乐的 `original/zero` 元数据不代表甜度筛选已接通。详细数据与导入证据见 [零食交付记录](work/snack-selection/IMPLEMENTATION.md)。

2026-10-03 对当前本地开发库的只读查询发现：合并的来源目录中有 `Orange Juice` 等果汁及零食样候选，并有演示店可售库存；其中文名称、类目和配料映射仍需核对，例如果汁记录的中文名为“Florida's Natural 橙子”、类目为水果。fixture 缺项不等于运行库没有供给，库存记录存在也不代表“果汁”等用户输入已能准确检索并采购。先整理现有候选与对应 Offer，再决定是否补充数据；这项数据盘点当时为只读，后续限定案例的模型检索与服务验证见 [修复记录](work/model-timeout-case/IMPLEMENTATION.md)，商品和索引未调整。

## 阶段验收

“稳定”先落到明确、可复现的演示范围。以下九类流程在执行前收敛为固定用例；按用户确定的口径，每个用例在相同冻结版本下独立重复 2 次，全部符合预期后进入当前阶段的演示验收：

1. **点名菜品**：实际可售商品、包装、购买数量和金额与业务数据一致，用户确认前不加购。
2. **模糊需求推荐**：必要澄清可正常完成或跳过；推荐一道可采购的菜，并说明有依据的理由。
3. **单菜换或撤回**：换菜重新检索与校验，撤回不加购；普通 ACK 不作为执行授权。
4. **追加与关系澄清**：追加第二道菜保留第一道；已有菜品清单中明确追加商品也保留原分组，数量符合分组贡献。未说明追加或替换关系时先澄清，不改写原清单。
5. **采购改选与确认**：勾选原本未选的调料、取消某项选择后，展示金额、后端快照和购物车新增结果一致。
6. **供给不足**：可售商品和缺项明确展示为预览，采购清单与购物车保持不变；用户决定后按其选择继续。
7. **具名商品选购**：检索到的商品符合用户点名目标，规格、销售包装、数量和金额与业务数据一致，明确确认前不加购。
8. **品类或消费偏好需求**：分别验证“吃点零食”“喝点果汁”等品类请求，以及“喝点甜的”等偏好请求；供给和商品资料足够时给出有依据的单款主推，必要澄清能完成，用户选定后准备清单。资料不足时明确说明，不能编造匹配依据。
9. **商品无匹配供给**：没有用户要求的商品、品类或满足条件的候选时明确说明，不用无关商品替代；旧清单与购物车保持不变。

具体用例与供给范围在正式执行前固定，覆盖本阶段确认的菜品、零食和饮品请求，以及已有清单时的关系澄清；商品选购的通过不能由菜品流程通过代替。

核对明确预算与食材排除约束；错报商品事实、静默放宽条件、错误加购和丢失已有分组的次数必须为 0。记录轮次、时长、失败和超时，不在看到结果后调整通过口径。

模型响应可靠性与回复速度是当前首要验证项：复测“来点零食”及后续追问，核对语义结果、超时分类和清单保留，同时记录首次反馈及最终回复耗时。速度门槛在该案例的受控实测后、正式演示验收前固定；不能仅凭错误返回更快认定性能已修复。

证据绑定源码及未提交改动快照、数据、索引、用例、模型及 Prompt 配置。真实前端操作必须与后端结果对应；单个 API、mock 或历史窗口通过不能代替本阶段端到端证据。

以上是本阶段口径，不替代或降低现有语义 TASK 的原约定，也不自动把任何 TASK 改为已验收。此前超时与品类语义修复见 [原交付记录](work/model-timeout-case/IMPLEMENTATION.md)，本轮成功零食供给与无匹配固定案例见 [零食 TASK](tasks/snack-selection.md)。两项零食闭环通过不代表饮品、偏好匹配、主推理由或整个阶段验收通过。历史阶段全量 A/B 不自动恢复。

## 选做与后续方向

- **选做：轻量忌口画像**。按当前匿名用户身份保存用户明确要求长期使用的食材排除项，提供查看、修改和删除，新会话可以读取。当前会话的临时表达不自动写成长久偏好；保存、当前会话调整和旧方案之间的作用范围在选做实施前明确。现有 cookie 身份不代表跨设备账号。
- **后续：自动记忆机制**。参考 `reference/learn-claude-code` 的 user、feedback、project、reference 分类及按需读取、提取与整理流程，暂不整体迁入。四类记忆不是当前菜品采购闭环的必要前提。
- **后续：菜与菜的关系及推荐**。在逐道采购稳定后，再考虑菜品搭配、整餐组合、共享食材利用和关联推荐。
- **后续：完整品类内选购**。在基础商品选购之外，单独收敛结构化筛选、差异比较及用户选择，不用当前菜品采购或基础商品选购的演示结果代替其验收。
